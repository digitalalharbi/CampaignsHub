# CI speed — measurement and design (CI-SPEED-002), 2026-11-19

Owner's order: PR CI takes about an hour and fails; make it fast (shards, caches, path filters, target under 10 minutes), cancel
superseded runs, never silently lose a deploy, lighten the nightly backend suite, keep builds off the VPS, watch Actions minutes.

Everything under "Before" was read from the Actions API on 2026-11-19 (`gh run list`, `gh api .../runs/<id>/jobs`, job logs).
Everything under "After" is **a design and an expectation, not a measurement** — the first run of the pull request that carries
this change is the measurement (see "What to compare").

### Where the hour goes

1. **Queue wait**, not setup. Medians of 6–15 minutes and maxima of 38–46 minutes before a job starts. Cause: 20 seats against
   ~12 per PR, several PRs per hour, and 47% of runs ending cancelled (a cancelled run still held seats while it ran — one
   cancelled run was 46 minutes old). Setup is small: composer 8 s, npm cached, browsers cached.
2. **Slow tests.** The chromium gate: 1,889 tests, 84 minutes of test time. It is cut into four contiguous slices of 27.2 / 20.6 /
   19.3 / 16.9 minutes (measured per-test times), so the wall clock is the slowest slice. **The physical floor is a file:**
   `agency-fit-2.spec.ts` is one file, 312 tests, **16.4 minutes** (next: `agency-fit.spec.ts` 8.7, `first-viewport-sweep.spec.ts`
   6.4). Playwright keeps a file's tests together, so no number of shards takes the chromium gate below about 17 minutes of tests
   (plus ~2.5 of setup and the global reset/seed) until that file is split.
3. **Genuine failures, not flakes.** Of 105 completed PR runs in the last 200, 62 failed (59%). In the 16 read in detail:
   `frontend` failed in 13 — the same unit test, `surfaceIntegration.test.tsx › adds the Insights tab…` (a renamed tab; the log
   says `Unable to find role="tab" and name "Insights"`; 5,428 of 5,429 pass); chromium shards failed in 11 runs on named specs
   (`mobile-hierarchy.spec.ts:16`, `advertiser-portal.spec.ts:74`, `platform-within-objective.spec.ts` x8, `one-ad-level.spec.ts`
   — UI renames from the analytics work leaving specs behind), repeated across pushes of the same branch. No `toomanyrequests`,
   no webkit "internal error", no timeout among them. Ranked: (1) stale unit/e2e specs after UI changes, (2) queue wait inflating
   every run, (3) superseded runs holding seats. Infrastructure flakes did not appear in this sample.
4. **Deploy proof gap** (below).
5. **Cache pressure.** `actions/cache` holds 11.0 GB in 166 entries against the 10 GB cap: `playwright-*` 24 entries / 6.8 GB (keyed
   by `package-lock.json`, a new ~300 MB cache on every unrelated dependency change), `apt-debs` 63 / 2.0 GB (per-run keys),
   `node-cache` 1.6 GB, `buildkit-blob` 0.9 GB. Over the cap GitHub evicts the oldest first — the Docker layer cache among them.

## Expected result (expectation, not measurement)

| PR type | Critical path | Expected wall clock, no queue |
|---|---|---|
| docs-only | changes (~20 s) + guards (setup ~1.5 min + tests) | ~4–6 min |
| backend-only | changes + static (4.8) or the slowest of 8 shards (~7) + image (~2–5 with layer cache) | **~8–10 min** |
| frontend-only | changes + chromium slowest shard (~17 tests + ~2.5 setup) ; frontend unit ~4 | ~20 min |
| backend + frontend | as frontend-only, with 8 + 3 + 6 + 3 jobs in parallel | ~20 min |
| the PR being landed (`full-gate`) | all three browsers, full backend: firefox/webkit shards unchanged (~20–27 min) | ~27 min |

**The 10-minute target is met only for docs-only and backend-only changes.** For anything touching `frontend/` it is bounded
below by `agency-fit-2.spec.ts` (16.4 min). To get under 10 there, that file must be split (e.g. into 4 files, or
`test.describe.configure({ mode: 'parallel' })` so Playwright can shard its tests) — a change to the specs, with their state and ordering to
review, deliberately not made here. Expected effect of that split alone: chromium critical path ~12 min with 8 shards.

Seats: one frontend PR needs 1 + 1 + 3 + 1 + 6 = 12 at once (was 12), a backend PR 1 + 1 + 8 + 1 = 11. Total runner time falls
(a docs PR ~10 runner-min against ~170; a backend-only PR ~75; a frontend-only ~110) so the queue wait — the largest measured
cost — should fall with it. That is also an expectation.

## Risks and what was not done

* **Backend-only PRs no longer run the browser gate** (the owner's order). A backend change that breaks the UI is found by the
  `full-gate` run when the Lander lands the PR, not by the PR's own CI. `backend/database/**` still starts it. Revert by
  adding `backend/` to the `e2e` rule in `ci-changes.py`.
* **Frontend-only PRs run `backend (guards)`, not the full suite**; backend tests that read frontend sources run, the rest do not.
* The 8-shard backend and 6-shard chromium weights are static; as tests are added the slices drift. The verdicts prove
  coverage whatever the weights say. Re-cut from the shard `run.json` artifacts (`backend-test-seconds.json`, `weights:`).
* The nightly run no longer exercises the suite as one process (see its header). Dispatch `single_process: true` for that.
* Not changed: `gate-allowed-skips.json`, the skip policy, `gate-verdict.py`, firefox/webkit sharding, the required-check names.
* Not done: splitting `agency-fit-2.spec.ts`; apt-debs per-run cache keys (2 GB churn); `~/Developer/ch-scripts` (outside the repo).

## Deploy proof

`deploy-production.yml` already queues deploys and never cancels a running one. GitHub keeps ONE pending run per group; a newer
pending run replaces an older one, and the replaced run finishes as `cancelled` without starting a job. Measured 2026-11-18:
5 of 25 deploy runs (`db8db94e` #1164's merge, `04dab5f4`, `ee3a0d27`, `cf99ccce`, `0e079727`) were replaced by a later push
(after 20 seconds to 39 minutes, depending on how long the running deploy took). What ships is unaffected — each deploy builds the commit that triggered it and the newest always runs, so
main is what ends up live — but `ch-scripts/verify-deploy.sh` takes `gh run list --commit <merge sha> --limit 1`, reads
`cancelled`, and reports `DEPLOY <pr> <sha>: run <id> cancelled`, which is how #1161's deploy "could not be proven".

**Gap (not fixed here, outside this repository):** `verify-deploy.sh` should treat `cancelled` as "superseded" when a later
`Deploy Production` run on a descendant commit succeeded:

```sh
# after: concl=cancelled for $rid on $sha
later=$(gh run list -R $R --workflow "Deploy Production" --status success --limit 20 --json databaseId,headSha,createdAt \
  --jq '.[].headSha' | while read -r h; do gh api repos/$R/compare/$sha...$h --jq '.status' 2>/dev/null | grep -qx -E 'ahead|identical' && echo $h && break; done)
[ -n "$later" ] && echo "DEPLOY $pr ${sha[1,8]}: superseded by successful deploy of ${later[1,8]}" && concl=success
```

then continue to the health/bundle checks, which prove what is actually served. Needs a test in the style of `test_refresh.sh`
with a stubbed `gh` before it is wired into the Lander; left for that change.

## Actions minutes

The repository is **public** (`gh api repos/digitalalharbi/CampaignsHub --jq .visibility` -> `public`), and GitHub does not bill
standard hosted-runner minutes for public repositories; the Free plan's limit that matters is **20 concurrent jobs**. The account
billing endpoint (`/users/<u>/settings/billing/actions`) answered 404 and the cache-usage call needs the `user` scope for billing, so
no invoice figure is claimed. `docs/ci/actions-usage.sh [N]` is read-only and prints runner minutes per workflow and job name for
the last N runs, plus cache usage against the 10 GB cap. Reference (this analysis): ~170 runner-min per PR run before the change;
the nightly job ~60–70 runner-min a day either way.

## What to compare (first run of the PR that carries this change)

1. `changes` job: its summary table matches the PR's files; ~20 s.
2. Run wall clock and per-job duration/queue for the same job names: `backend (tests i/8)` (target ~7 min), `frontend (unit i/3)`,
   `gate shards (chromium) / shard i/6` (slowest ~19 min; is shard 2 `agency-fit-2` alone?), `image` (before 4.4 min; layer cache hit?).
3. This PR touches `.github/`, so the classifier answers "everything": a full run — compare it to the medians above, not to the
   expectations for a docs or backend PR. Then push a docs-only commit and a backend-only commit to a scratch branch to read
   the filtered paths (`backend (guards)` duration, `backend` / `frontend` / `image` / `gate (chromium)` green with "not needed").
4. Required checks present and SUCCESS on all of those; `waitpr.py` prints GREEN; label `full-gate` starts firefox + webkit + the
   full backend.
5. `docs/ci/actions-usage.sh 30` before and after: runner-min per workflow; cache usage (should stop growing with Playwright keys).
6. Next 01:00–02:00 Riyadh: `Backend full suite (nightly, sharded)` ran at ~21:37 UTC, 8 shards, verdict green.
