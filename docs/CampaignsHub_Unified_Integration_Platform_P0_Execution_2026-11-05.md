# CampaignsHub — Unified Integration Platform
## عقد تنفيذ ملزم P0 | 2026-11-05 | تحديث تراكمي دون إسقاط المتطلبات السابقة

> **هدف المهمة:** إعادة هندسة منظومة التكاملات **داخل CampaignsHub القائم** لتكون منصة تكاملات موحدة ومستدامة ومتعددة المستأجرين (Multi-Tenant)، وفق Project-First Resource Linking، دون نظام منفصل أو تكرار محركات موجودة أو تعطيل أي تكامل عامل.
>
> **درجة الإلزام:** كل بند أدناه قابل للتتبع بمعرّف ومعيار قبول ودليل. لا يجوز الاكتفاء بالتوثيق أو UI أو نجاح الاختبارات لإغلاقه. لا توجد ضمانة تقنية «صفر أخطاء مطلقًا»؛ البديل الإلزامي هو اكتشاف الأخطاء مبكرًا، ومنع التسرب والفساد، والتحقق التدريجي الحي، والتراجع الآمن.

## 0. السلطة والتراكم والاستمرارية

1. المرجع الأعلى **للحالة الحالية**: `origin/main` ثم PR/CI/Deploy الفعلي، تليه `docs/REQUIREMENTS_TRACEABILITY_MATRIX.md` و`docs/OWNER_OBSERVED_DEFECTS.md` و`docs/RESUME_STATE.md`، ثم ملفات التسليم والسياق السابقة. الأحدث تصحيحًا يلغي المتعارض فقط.
2. هذا **تطوير متصل للمشروع نفسه**؛ لا يُنشأ Microservice أو تطبيق SaaS جديد أو مركز تكاملات موازٍ دون دليل ضرورة واعتماد صريح. إعادة استخدام ما هو موجود أولًا؛ لا تُعاد وظائف VERIFIED دون خلل مثبت.
3. احتفظ بالأولويات الأمنية الجارية وبالبنود السبعة P0 والمهام المعتمدة سابقًا (Meta، المعاينات، GA4/المتاجر/المؤثرون والإسناد، الموافقات، التحكم بالتحقق، البريد، الأداء)، وكذلك سلامة فلاتر وتقارير Live/Snapshot، والعملات، دون استبدال تكليفاتها بهذا المستند.
4. **لا تجزّئ تجربة المستخدم على عدة مراكز ربط**: مركز مرئي واحد يخدم المشاريع، وفهارس وإدارات مركزية لمالك الصلاحية. لا تعطل الرخص والروابط والاتصالات الحالية عند الترحيل.
5. الحالات الوحيدة للتقدم: `NOT_STARTED`، `IN_PROGRESS`، `PARTIAL`، `IMPLEMENTED_NOT_VERIFIED`، `VERIFIED`، `BLOCKED_EXTERNAL_CREDENTIALS`، `BLOCKED_OPERATIONAL_EVIDENCE`؛ اذكر حالة مستقلة لكل وحدة ولكل مزود.
6. لا تفتح عددًا غير محدود من الفروع أو الوكلاء: Worktree مستقلة لمهمة غير متعارضة، PR صغير قابل للدمج، دمج متسلسل عبر Lander، والنشر والتحقق قبل استهلاك طابور إضافي. حافظ على الأعمال غير المدمجة بالفعل.

## 1. المتطلبات الأصلية الملزمة — جميع البنود الستة عشر دون إسقاط

### 1.1 تدقيق المستودع والاستفادة من الموجود
افحص كامل مستودع GitHub والواجهات وAPI والـAdapters وقواعد البيانات والـJobs والـWebhooks. احصر التكاملات الحالية ومشكلاتها واعتمادياتها **قبل التعديل**. اجعل التدقيق سريعًا وموجهًا للتنفيذ لا مشروع توثيق مستقلًا.

### 1.2 محرك Integration Core موحد
أنشئ أو وحّد المكونات القائمة داخل المنظومة نفسها بحيث تشمل:
- Provider Registry & Capabilities.
- Authentication / OAuth / API Credentials.
- Resource Discovery.
- Project Resource Bindings.
- Sync & Webhook Engine.
- Credential Lifecycle.
- Audit Logs & Health Monitoring.

### 1.3 رحلة الربط الإلزامية
**اختيار المشروع ← المزود ← التفويض الرسمي عند الحاجة ← اكتشاف الموارد ← اختيار المورد المحدد ← تأكيد الربط ← التحقق ← المزامنة ← إظهار الحالة الفعلية.**
لا يتحول مورد مكتشف إلى مورد مرتبط تلقائيًا، ولا يطلق التفويض أو الاكتشاف مزامنة جماعية.

### 1.4 المزودون والنطاق
ادعم جميع المزودين الحاليين: **Snapchat وTikTok وMeta وGoogle Ads وLinkedIn وX وOpenAI Ads (ChatGPT Ads) وGA4 وسلة وزد**، إضافة إلى أي تكامل موجود فعلًا في المستودع. جهّز بنية تدعم إضافة **Shopify وWooCommerce وGoogle Sheets وSearch Console وGTM وCRM** لاحقًا عند اعتمادها، **دون إنشاء تكاملات خارجية غير مطلوبة أو غير معتمدة**.

### 1.5 هوية المورد حسب المزود
| فئة المزود | المورد الأساسي |
|---|---|
| Ads | Ad Account |
| GA4 | Property |
| Commerce | Store / Merchant |
| Sheets | Spreadsheet / Sheet |
| CRM | Workspace / Pipeline |

لا تستخدم مفتاحًا عامًا غير مناسب يجبر كل المزودين على مفهوم Ad Account.

### 1.6 فصل المفاهيم
افصل **التفويض Credential/Connection** عن **المورد الخارجي Resource** عن **ربطه بالمشروع Binding** عن **تشغيل المزامنة Sync Run**. لا تعني صلاحية رؤية مورد حقًا لربطه أو مزامنته في كل المشاريع.

### 1.7 قاعدة البيانات والعزل
صمم علاقات واضحة وقيود uniqueness محسوبة، مع مفاتيح Tenant/Workspace/Project/Provider/Resource/Binding، ودعم الموارد المشتركة **فقط عندما يكون التفويض بها صريحًا**. امنع التكرارات والقراءات والكتابات المتقاطعة. لا تفترض ملكية مورد بالاعتماد على اسم الحساب وحده؛ تحقق من المعرف الرسمي والتفويض وحدود المستأجر.

### 1.8 Provider Adapter Contract
عرّف Contract موحدًا بقدرات **اختيارية**؛ لا تفترض أن كل مزود يدعم OAuth أو Webhooks أو Refresh Tokens أو Hierarchy أو نفس حدود الطلبات. طبّق التكييف حسب توثيق المزود الرسمي وقدرات التطبيق المصرح بها، مع ميزات غير متاحة تُعرض بصراحة.

### 1.9 محرك المزامنة
مزامنة لكل Binding/Resource، مع Incremental Sync وCursor وCheckpoints وIdempotency وRetries وBackoff وRate Limits وDead Letter Queue وRecovery، وتحكم مركزي بجدولة مهام متوازنة ومنع التداخل. لا تُحذف بيانات عند فشل صفحة أو دورة مزامنة، ولا تستبدل نجاحًا قديمًا ببيانات ناقصة بلا بيان.

### 1.10 Webhook Engine
تأكيد التوقيع ومصدر الحدث، replay protection، deduplication، ترتيب وتحمل التأخر وخروج الأحداث عن الترتيب، retry/replay الآمن، والمطابقة الدورية؛ خصوصًا للمتاجر والطلبات. لا تعتبر Webhook مؤكدًا لمجرد وصول HTTP 200.

### 1.11 نموذج البيانات والمقاييس
وحد طبقة التعريفات والربط للإعلانات والتحليلات والمتاجر مع **حفظ semantics والمصدر والعملة والفترة الزمنية وتعريف التحويل**. لا تجمع مبيعات GA4 أو المنصات أو المتاجر كإيراد موحد دون قواعد reconciliation/dedup موثوقة. المصدر الأساسي للمبيعات الفعلية هو سجل الطلبات المؤكد من المتجر؛ أبقِ إسناد المنصات تقديرًا منفصلًا.

### 1.12 مركز الربط عربي RTL وProject-First
واجهة سريعة وخفيفة من ثلاثة أقسام واضحة:
1. **المشاريع**: ابدأ من مشروع ثم مزود وربط مورد محدد.
2. **المصادر المرتبطة**: الموارد الفعلية والحالات والتحكم.
3. **التدقيق**: صحة الاتصال والتفويض والسجلات والمزامنة والأخطاء.
مع البحث والتصفية وإعادة المصادقة والمزامنة والفصل الآمن، وإدارة مركزية للصلاحيات المناسبة، مع دعم AR/EN وRTL/LTR والجوال.

### 1.13 حالات مستقلة وصادقة
اعرض بصورة مستقلة: **حالة التفويض، حالة ربط المورد، حالة المزامنة، حداثة البيانات، حالة الخطأ**، مع آخر نجاح/فشل وخطوة علاج عملية. المكتشف ليس مرتبطًا، والمتصل ليس متزامنًا، والناجح API لا يعني اكتمال البيانات.

### 1.14 ترحيل تدريجي
نفّذ Migration/Backfill تدريجيًا وآمنًا، مع Backward Compatibility وRollback وخطة cutover واضحة **دون حذف الروابط أو السجلات التاريخية** ودون تشغيل مسارين متنافسين يكتبان البيانات نفسها. احتفظ بهويات وعلاقات الموارد والتقارير الثابتة والمحفوظة.

### 1.15 الاختبارات
Unit وIntegration وE2E وSecurity وMulti-Tenant، وخاصة عزل العملاء، اختيار مورد واحد، انتهاء التفويض، تعدد الموارد، duplicate/out-of-order webhooks، منع المزامنة الشاملة، وتطابق الأرقام قبل الترحيل وبعده. اختبر الواجهات الفعلية وخطوات الرفض بقدر مسارات النجاح.

### 1.16 قابلية التوسع والتشغيل
وثائق تقنية قصيرة، Runbooks تشغيلية، Provider SDK داخلي فعلي وقابل للاستخدام، وإجراءات إضافة Adapter جديد دون إعادة تصميم المحرك، مع سياسة capabilities واضحة واختبارات contract ثابتة.

## 2. التصميم المنطقي المقترح — يُراجع مقابل البنية الموجودة ولا يُفرض كتكرار لها

التكوين المفاهيمي لا يلزم أسماء جداول جديدة متى وُجدت مكافئات موثوقة:

- `ProviderDefinition` (معرّف فريد، capabilities، resource types، health policy).
- `ProviderConnection`/`CredentialGrant` (tenant، نوع التفويض، scopes، expires_at، secret reference، ownership).
- `ExternalResource` (provider + provider_resource_id + resource_type + ownership، metadata آمنة).
- `ProjectResourceBinding` (tenant/project/resource/grant، state، selection provenance، sync_enabled، timestamps).
- `SyncCheckpoint`/`SyncRun`/`SyncJob` (binding، cursor، time window، idempotency key، retry details).
- `WebhookInbox`/`DeliveryAttempt` (provider/event id/hash، timestamp، signature verdict، status، correlation id).
- `IntegrationAuditEvent` (actor، action، resource، scope، قبل/بعد مع تنقية الأسرار).

**قواعد لا تقبل الاستثناء:** لا credentials في السجلات أو الواجهة؛ قيد server-side على Tenant/Project/Binding في القراءة والكتابة والـexports والتقارير؛ المصدر المكتشف يظل غير مفعل؛ التحويل بين الحالات explicit عبر API لا بالانتقال بين صفحات UI. استعمل encryption/rotation/revocation الموجود ولا تكرر نظام خزنة.

## 3. مصفوفة احتمالات وحالات حافة إلزامية

| الحالة | الاستجابة المطلوبة |
|---|---|
| حسابان إعلانان تحت التفويض نفسه؛ اختير أحدهما | ربط ومزامنة المختار فقط؛ الآخر مكتشف غير مرتبط |
| خاصيتان GA4 في الحساب نفسه | لا تُزامن إلا Property المختارة |
| متجران سلة/زد لدى نفس التاجر | لا تدخل أي طلبات أو منتجات من متجر غير مختار |
| مورد مشترَك مصرح به بين مشروعين | Binding مستقل وقيد نطاق لكل مشروع؛ لا تكرار أو تسرب بيانات |
| حساب أو Property تغير اسمها أو موضعها | الهوية بالـprovider ID، وليس الاسم النصي |
| انتهاء التفويض، revoked scope أو token refresh فاشل | حالة Reconnect صادقة، توقف المهام المعنية وحدها، دون إفساد بقية المشاريع |
| مزود API Key دون OAuth | مسار مستقل صالح، لا طلب Refresh Token وهمي |
| مزود بلا Webhooks | Polling مع checkpoints واستدراك آمن |
| Webhook مكرر أو متأخر أو خارج الترتيب | idempotent، لا ازدواج طلبات ولا تراجع نسخة أحدث |
| 429/5xx/timeouts/partial pages | retry/backoff ضمن budget، checkpoint آمن، لا يُسجل نجاح كاذب |
| Task عامل أثناء فصل Binding | قفل آمن؛ لا كتابة بعد الفصل؛ إمكانية إعادة التوصيل بتفويض جديد |
| ربط مورد بعد نقله بين Tenant/Project | إعادة تحقق صلاحيات لا نقل صامت للمحتوى التاريخي |
| نفس Campaign ID عبر حسابين أو مشروعين | لا توحيد بالمعرّف الجزئي؛ مفتاح مركب ونطاق صريح |
| فشل التخزين أو cache stale | fail closed للصلاحيات، لا fallback يعرض نطاقًا أوسع |
| تقرير Live/Snapshot/Preview/PDF/CSV/XLSX | نفس سقف الموارد والمشاريع والعملات لكل سطح، مع حماية النسخ القديمة عند القراءة |
| حملات بعملات متعددة | احتفظ بالأصل وFX provenance؛ لا جمع مختلف العملات ولا تحويل تخميني |
| عبء مزامنة كبير أو onboarding متعدد | عزل queue وrate budget لكل مزود/Binding؛ سرعة التصفح لا تُربط بنهاية Sync |
| الموارد الحالية لا تملك Mapping كاملًا | توثيق mapping والرفض الآمن دون حذف البيانات؛ dry-run ومراجعة الفروق قبل cutover |
| القيم محجوبة بسبب Credentials/Scopes | لا تُعرض كصفر موثوق أو Connected/Healthy كاذبة |

## 4. خطة التنفيذ الإلزامية — مراحل قصيرة قابلة للنشر

### المرحلة A — Inventory & Gap Map
- اقرأ الـGit الفعلي والفروع والـPRs، ومصفوفة المتطلبات، وأي Integrations Center/Provider Registry/Adapters/Connection Vault/BoundAccountVisibility/Sync Jobs قائم.
- قدّم *فرقًا قابلًا للتنفيذ* بين الموجود والمطلوب لكل مزود. صنّف VERIFIED، PARTIAL، IMPLEMENTED_NOT_VERIFIED، العوائق الخارجية.
- أضف صفوف المصفوفة الناقصة فقط، ثم ابدأ تنفيذًا ولا تنشغل بتقارير مراجعة متكررة.

### المرحلة B — حماية الحدود أولًا
- أضف أو ثبّت اختبارات fail-first لكل Tenant/Project/Resource/Binding.
- أغلق مسارات الربط والمزامنة الضمنيين والتسرب بين التقارير والـAPI والـjobs والـwebhooks.
- احتفظ بعزل التقارير وأحدث إصلاحاته؛ لا تتراجع عن #962 وما يليه.

### المرحلة C — توحيد Core والـAdapter Contracts
- أعد استخدام الخدمات القائمة، وألغِ التفرع المتكرر تدريجيًا بدل تكرار الأنظمة.
- أنشئ contracts/capability negotiation بميزات اختيارية وadapter contract tests.
- أغلق provider-specific gaps واحدًا واحدًا دون استبدال all-at-once.

### المرحلة D — Project-First Wizard ومركز التكاملات
- نفّذ رحلة ربط فعالة من المشروع إلى المورد مع حالات مستقلة والتحكم في sync per binding.
- اختبر على بيانات معزولة أن تغيير الاختيار يغيّر binding والـAPI ونتائج المزامنة فعليًا، لا checkbox بصريًا.
- حافظ على الدخول الموحد والأدوار وواجهات الوكالة والعميل.

### المرحلة E — Sync/Webhook & Observability
- استكمل incremental/resume/retry/DLQ وdedup/reconciliation حسب قدرة كل مزود.
- أثبت عدم إطالة تحميل الصفحة عند مزامنة عالية الحمل؛ استخدم metrics قبل/بعد على حمل مماثل.
- أضف سجلات دقيقة لا تكشف بيانات سرية، وعمليات retry/replay مقيدة بالصلاحيات.

### المرحلة F — Provider-by-Provider Migration
- لكل مزود قائم: baseline قبل الترحيل → mapping → dry-run/diff → backup/rollback → feature flag/canary → cutover مع كاتب واحد → readback reconciliation → production verification.
- امنع dual writes لنفس البيانات، ولا تحذف تاريخًا ولا تغيّر connected resource IDs دون خطة وrollback.
- حالة Meta/ TikTok/ChatGPT Ads وغيرها التي تحتاج مفاتيح/موافقات تُسجّل كعائق خارجي **فقط للخطوة التي تحتاجها**؛ استمر في بقية الوحدات الممكنة.

### المرحلة G — Acceptance & Operations
- Unit/Integration/E2E/Security/Multi-Tenant/Load + اختبارات متصفح AR/EN، وReplay/Recovery وRBAC.
- في نهاية كل دفعة: CI → Merge via Lander → Deploy → Production readback → تحديث المصفوفة والسجل؛ لا تعتبر deploy=VERIFIED.
- توثيق إضافة adapter والعمليات التشغيلية/rollbacks من التنفيذ الحقيقي وليس وصفًا تخيليًا.

## 5. معايير القبول الأصلية — بوابات لا يجوز تجاوزها

1. ربط حساب واحد **لا يؤدي إلى مزامنة بقية الحسابات**.
2. ربط خاصية GA4 **لا يستورد بقية الخصائص**.
3. ربط متجر سلة أو زد **يعالج بيانات المتجر المحدد فقط**.
4. كل مشروع **يعرض مصادره الفعلية دون اختلاط العملاء**.
5. إضافة مزود جديد **لا تتطلب تعديل منطق المحرك الأساسي**؛ يكفي Adapter/Registry/Capability المعياري إلا عند توسيع contract بإصدار مضبوط.
6. جميع التكاملات الحالية تستمر **دون فقدان بيانات أو روابط أو تقارير تاريخية**.
7. توجد **مراقبة دقيقة وإعادة معالجة آمنة للأخطاء**.
8. نجاح الاختبارات والتحقق الإنتاجي بالأدلة، **دون ادعاء تحقق حي** لمزود لا تتوفر بياناته أو صلاحياته.

**إضافات حماية القبول:**
- نجاح الفلاتر في UX لا يكفي: نفس scope في HTTP/API/DB/queue/webhook/report/export.
- يجب إثبات الفشل المقصود (denial) في السيناريو غير المصرّح، لا النجاح فقط.
- لا تغيير مفاجئ في الحسابات المرتبطة أو جداول المزامنة أو أرقام الإنفاق أو الطلبات؛ reconciliation بأرقام قبل/بعد.
- لا mark VERIFIED لمجرد الاختبارات أو وثيقة أو واجهة Demo.
- لا عمليات destructive أو mass reauthorization/migration حية دون تفويض صريح.

## 6. سجل التتبع الذي يجب تحديثه بعد كل دفعة

كل عنصر يُسجّل بمفاتيح ثابتة: `Requirement ID`، المزود/الوحدة، حالة البداية، العيب المثبت، branch/PR/SHA، اختبار fail-first، CI، deploy SHA/run، evidence query أو screenshot، المقارنة قبل/بعد، الحالة النهائية، blocker والخطوة التالية. لا تزدوج السجلات ولا تضف مصفوفة متطلبات ثانية.

## 7. أمر التشغيل المعتمد

اقرأ هذا الملف كاملًا واعتمده عقد تنفيذ تراكمي P0. استأنف من `origin/main` وPRs/Worktrees القائمة، احصر الموجود بسرعة، ثم نفّذ الفجوات فقط في دفعات صغيرة ذات أولوية أمنية، مع الحفاظ على كل VERIFIED. اعمل باستقلالية في القرارات الهندسية الروتينية. لا تُنشئ منصة موازية، ولا تحوّل Discovery إلى Binding، ولا تسمح بمزامنة موارد غير مختارة أو تسرب بين Tenant/Project. مرّر كل دفعة عبر اختبار fail-first وCI وLander وDeploy والتحقق الإنتاجي والأدلة، ثم استمر تلقائيًا. أي مفاتيح/موافقات خارجية أو عمليات إنتاجية عالية المخاطر تُعرض كعائق محدد دون تعطيل بقية العمل.
