## AU-001 — مركز الجمهور الموحد
- قسم «الجمهور» في التحليلات، وصفحات العميل، والتقارير المباشرة والمحفوظة والمشاركة والتصدير؛ يُفعل بصلاحية وبحسب توفر البيانات، مع إعدادات إظهار/إخفاء **مستقلة** لكل نوع بيانات: المناطق، المدن، الجنس، العمر، الأجهزة، مواضع الظهور، الاهتمامات، المؤشرات المهنية الخاصة بـLinkedIn، الجمهور المستهدف، الجمهور الفعلي، تحويلات الموقع/GA4، الاستهداف الجغرافي، الإنفاق ونتائج كل تقسيم، وتوصيات التحسين. لا تكشف حقولًا مخفية في HTML أو JSON أو PDF أو تحميلات الملفات أو الطلبات المباشرة، مع حماية المسارات API على الخادم.
- لكل بند من الجمهور: اسم المنصة، الحساب، المشروع، الحملة، المجموعة أو مستوى الاستهداف الحقيقي، مقياس النسبة وبسطها/مقامها، الفترة الزمنية، عملة الإنفاق ومصدرها، تاريخ المزامنة، الأهلية، اكتمال التغطية. عدم وجود تقسيم في API ليس قيمة صفرًا ولا دليلًا على عدم وجود مستخدمين.
- ميّز دائمًا: (أ) **المطلوب من العميل** بخطة معتمدة، (ب) **إعدادات استهداف الإعلان**، (ج) **تسليم مدفوع مثبت** عبر breakdown المنصة، (د) **أحداث الموقع** عبر GA4 أو المتجر، (هـ) **مشاهدات أو مشاركات غير مدفوعة**. ممنوع دمجها في حقل واحد أو وصف إحداها بأنها الأخرى.
- اجمع المنصات في لوحة مقارنة فقط عندما يتطابق التعريف والتغطية؛ مجموع الظهور/النقرات مع التسمية والمصدر ممكن بعد منع التكرار، لكن **الوصول الفريد عبر المنصات لا يُجمع كأشخاص فريدين**، والذكور/الإناث والأعمار والنسب لا تُجمع بجمع النسب أو متوسطها؛ اشتق النسبة من نفس المقام والمقياس مع التصريح بأجزاء «غير معروف/غير متاح». إن لم يمكن المقارنة، اعرض كل منصة بجانب الأخرى.
- لا تنسب تحويلًا أو مشتريات لجنس أو عمر أو مدينة بلا تفصيل مُعطى من المنصة بتعريف صحيح؛ لا تستنتج demographics من GA4 للإعلانات. قيد الخصوصية أو نقص الصلاحيات = `UNAVAILABLE_PROVIDER` / `BLOCKED_EXTERNAL_CREDENTIALS` / `BLOCKED_OPERATIONAL_EVIDENCE` بحسب الإثبات.
- تصميم من شاشة قرار واحدة: مرشحات ثابتة (عميل/مشروع/فترة/منصة/هدف)، مؤشرات مختصرة ثم رسوم تتبدل حسب المقياس (شريط المناطق، توزيع الجنس، فئات العمر، الأجهزة) وقائمة فروقات قابلة للفتح؛ الجوال 320–430 لا يمرر أفقيًا، وتفاصيل الفلاتر داخل drawer/accordion. لا تنسَ لغتي AR/EN واتجاه RTL/LTR وLight/Dark، وإظهار المصدر والنسبة المقروءة.

## GEO-001 — حادثة ديوان القهوة 1KCOFFEE (12 نوفمبر 2026)
**النطاق الإلزامي: Snapchat وTikTok وMeta وX وGoogle Ads معًا.** العميل ذكر ظهور إعلان في مكة بينما أراد نجران. **ليس دليلًا أي مزود مسؤول، ولا دليلًا وحده أن الظهور ممولًا أو أن الاستهداف خاطئ.**
1. قراءة فقط في Production، وربط قائمة الحسابات والحملات/المجموعات الفعلية للعميل دون التخمين في أسماء الحملات. سجّل الحالة `فُحص/تعذر فحصه` لكل منصة مع السبب.
2. اعرض بشكل منقح: (أ) متطلبات العميل المعتمدة، (ب) المواقع المضمّنة والمستبعدة ونصف القطر/نوع الموقع/توسيع الاستهداف حيث تدعمه المنصة، (ج) حالة ووقت تغيير الإعدادات، (د) تقارير **التسليم المدفوع جغرافيًا** لفترة 2026-11-12 واسم حقل القياس، (هـ) سلوك الفيديو/المشاركات غير المدفوعة إن كانت الواقعة لقطة من عميل.
3. امنع مقارنة مدينة سكن الشخص بمدينة الاستهداف، أو موقع الجلسة في GA4 بمكان ظهور الإعلان المدفوع، أو إنفاق حساب كامل باستهداف مجموعة واحدة، أو نطاق 7 أيام بيوم واحد. استخدم zone/timezone المنصة، وقت الإعلان، ومصدر المنطقة وتغطيتها.
4. **لا تنبيه «الإعلان ظهر خارج نجران» إلا إذا توفر breakdown مدفوع موثوق وقابل للمقارنة، وتوافقت هوية المجموعة والفترة مع خطة الاستهداف المعتمدة.** إذا كانت البيانات لا تكفي: «تعذر التحقق من مكان الظهور» + السبب والإجراء الآمن، وليس ادعاء انعدام الخلل.
5. لا تغيّر استهدافًا حيًا، ولا تُوقف حملة، ولا ترسل رسالة اتهام إلى العميل أو فريق الحملات دون موافقة وعزل صلاحية. أدرج سجلًا تدقيقيًا لكل قرار وتغيير لاحق.
6. قبول GEO-001 = جدول من **خمسة صفوف** كل منصة وحالتها ومصدر API والدليل المنقح، ومثال حقيقي أو إثبات حجب صريح، واختبارات اختلاف النطاق والإعلان العضوي والخلط بين المدينة/المنطقة وغياب البيانات.

## MEDIA-ALL-001 — محتويات كل منصة، بلا تراجع
- منصات الإعلانات: Meta وSnapchat وTikTok وGoogle Ads وX وLinkedIn وChatGPT Ads حين يتوفر محتوى مدعوم. احصر الحسابات **المرتبطة فعليًا** ونوع الإعلان والعرض ووقت القياس، وقارن العدد المتاح في منصة الإعلان مع المحتوى المحفوظ والمعروض خلال الفترة/الحساب/التصفية نفسها.
- لكل منصة مستقلًا: OAuth/config → granted scopes أو نوع الوصول الفعلي → API status وresponse منقّح لعنصر واحد على الأقل → pagination → creative/post/media URN/IDs → ingest/DB → نسخ أغلفة آمنة وحالة صلاحية الرابط → frontend → `/r/...` → report saved/export → محتوى العميل، دون تغييرات غير لازمة في المزودين السليمين.
- **LinkedIn معلومة من Git عند إعداد هذه المواصفة:** `ProviderCatalogue::linkedin()` يعرّف افتراضيًا `['r_ads','r_ads_reporting']`. `PlatformCredentials::for()` قد يستبدلها بما وضعه مشرف المنصة عبر `ProviderConfigurationService::scopes()`؛ لذلك لا تجزم بالـeffective production scopes دون قراءتها. `PlatformOAuth` يبني scope من هذه القيم، و`OAuthTokens` يحتفظ بحقل `scope` عند إعادته. `TokenVault::open` يضع القيم المطلوبة عند غياب الحقل، فلا يصح تسميتها «ممنوحة فعليًا» إلا إذا أكدها رد المزود. المستخدم أكد اعتماد `r_organization_social` و`rw_ads` في تطبيق LinkedIn. اثبت طلبهما وحيازة التوكن ومخرجات Posts/Images/Videos دون عرض access/refresh tokens أو أسرار أو بيانات أشخاص. عند نقص التوكن المثبت اطلب تفويضًا جديدًا للحساب المتأثر فقط بعد الإثبات.
- **X:** تكامل Ads قائم OAuth 1.0a؛ endpoint التغريدات المروجة قد يعيد النص والصورة، وليس إثباتًا لجلب الفيديو الأصلي. قارن قيود وصول Ads والـmedia API الفعلية؛ لا تعد بفيديو/صورة لا يمنحها المزود أو التوكن. اعرض المحتوى النصي ووصف الاستثناء حين يلزم.
- لجميع الأنواع: صورة، فيديو، غلاف، النص الأساسي والعنوان، CTA والرابط، معاينة وتكبير وتشغيل/تحميل **إذا توفر أصل قابل للوصول وبإذن**، مع توضيح ما لا يتوفر. لا تغيّر المعروض في تقارير العملاء المنشورة دون اختبار regression، ولا تعرض صورة Placeholder كأنها أصل الإعلان.
- تقرير إغلاق MEDIA = تغطية (provider / account / ad type / source count / stored / rendered / available media / missing reason / verified live), والعجز الممنوع من المزود منفصل عن العيوب البرمجية. «100%» يعني اكتمال المتطلبات الممكنة ضمن صلاحيات المزود وثبوتها بمقارنة حية؛ غير المتاح يظل Blocked ولا يتخفى داخل VERIFIED.

## FIN-PLUS — قرارات مالية وعرض مرن (لا يلغي مواصفة المالية السابقة)
- رحلة واحدة: طلب حملة يمكن إنشاؤه **قبل** مشروع مكتمل → عرض سعر → موافقة العميل → إيصال → **مطابقة المالية مع البنك** → اعتماد تمويل → إنشاء/اختيار مشروع بلا ازدواج → ربط الحسابات → إطلاق الحملات → إنفاق المنصات → الرصيد والتنبيهات والتجديد.
- إيداع العميل ليس فاتورة، وحمل صورة إيصال لا يساوي وصول المال. يتولى مدير المشروع طلب الميزانية والتواصل مع العميل، وتقوم المالية بالمطابقة والاعتماد، ويدير فريق الإعلانات الإنفاق، وكل إجراء موثق بالفاعل/الوقت/الدليل دون إلقاء مسؤولية التحصيل على المختص.
- دفعات التمويل **تراكمية**؛ أضف Credit جديدًا عند التجديد دون تصفير الإنفاق أو تغييره، مع idempotency ومنع إعادة خصم إنفاق اليوم نفسه عند sync/reconnect. لا تدمج «حد إنفاق مراقبة» مع «رصيد التمويل المعتمد» ولا مع فواتير SaaS.
- الشاشة المالية **ليست نسخًا للصور المرجعية**: رأس قصير + فلاتر وسياق + أربعة مؤشرات (الميزانية المعتمدة والإنفاق والمتبقي وطلبات تنتظر المالية) + رسم رصيد تاريخي تُرى فيه قفزات التجديد + توزيع الإنفاق + قائمة عملاء مضغوطة بترتيب الحاجة لتجديد وفتح التفاصيل بدل تمرير أفقي. على 1366×768 تظهر الأرقام والرسم وأول عميل يحتاج قرارًا قبل التمرير، ولا يعد أحد بعرض 30 عميلًا بكامل سجلاتهم في شاشة واحدة؛ على الجوال بطاقات مختصرة وإجراءات قابلة للوصول.
- SAR معيار العرض مع حفظ مبالغ المصادر وسعر صرف يومي وتاريخه ومصدره، ولا تحوّل غير الموثق إلى صفر. التنبيهات (تم اعتماد التمويل / قرب النفاد / تجديد / نقص المستند / مزامنة ناقصة) للجهة المسؤولة فعلًا بصلاحية scoped وdedupe. لا إرسال فعلي دون تفويض وإثبات التسليم.

## تصحيح حاكم جديد MOBJ-2026-11-13 — أهداف متعددة داخل الحملة الواحدة
**مصدر القرار:** تصحيح المالك بشأن حملة «ديوان القهوة 1KCOFFEE» ذات مساري «الفروع» و«المتجر». **هذا التصحيح ينسخ فقط أي افتراض أقدم يجعل حملة كاملة ذات هدف قياس واحد، مع الإبقاء على كل متطلب آخر.**

### القاعدة
- لا تفترض أن الحملة الواحدة ذات هدف قياس واحد. **وحدة تصنيف نتيجة الأداء هي أدنى مسار إعلاني يملك هدفًا أو حدث تحسين ومبلغ إنفاق موثوقًا**: عادةً المجموعة الإعلانية (`ad_set/ad_group/line_item`)، مع أولوية لتوثيق المنصة الفعلي. في المنصات التي تحدد الهدف/الحدث على مستوى آخر، استخدم ذلك المستوى الموثّق؛ إن كان داخل المجموعة أكثر من وجهة/حدث مختلف، افصل على مستوى الإعلان/الحدث **فقط إذا أمكن نسبة الإنفاق لذلك المسار بدقة**. لا توزع الإنفاق بالتخمين أو بالانطباعات.
- ميتا: اقرأ هدف الحملة، `optimization_goal`، `promoted_object`، وجهة الإعلان، أحداث التحويل وقياسات المجموعة؛ افصل «زيارات الفروع» عن «مبيعات المتجر». Snap/TikTok/Google/LinkedIn/X: ابنِ خرائط خاصة بتوثيق كل مزود وموضع هدف التحسين أو الحدث وتغطية بيانات الصرف.
- حملة «ديوان القهوة»: **مسار الفروع = زيارات/زيارات صفحة هبوط عند قياسها فعليًا**؛ **مسار المتجر = مشتريات وإيراد وROAS**. تكلفة المشتريات وعائد الإنفاق تحسبان على **إنفاق مسار المبيعات فقط**، ولا تقسم الإيرادات على إنفاق الحملة المختلطة كلها. مسار الزيارات لا يُعرض «صفر نتائج» بسبب عدم وجود شراء.
- التقرير الإجمالي يعرض **إجمالي الإنفاق للحملة مرة واحدة** بوصفه مبلغًا ماليًا، وبجانبه **النتائج مفصّلة حسب الهدف/المسار**؛ لا تجمع عدد الزيارات والمشتريات والعملاء المحتملين في «نتائج» رقمية موحدة. أظهر ما لم يمكن إسناده بدقة كـ«إنفاق غير موزع» مع شرح السبب.
- عند انتخاب حملة مختلطة أو اختيار قالب تقرير «مبيعات» **لا تختفِ بقية حملات/مسارات الأهداف الأخرى** إلا باختيار فلتر استبعاد صريح من المستخدم. يمكن اختيار عدة أهداف في التقرير، ولا يغيّر اختيار قالب القياس مصدر الحقيقة.
- طبّق **نفس نموذج بيانات المسار** عبر التحليلات والحملات ومركز المحتوى ورابط التقرير `/r/...` والتقرير المحفوظ والتصدير PDF والملخصات اليومية/الأسبوعية/الشهرية والتنبيهات وبوابة العميل. التنبيه «تراجع العائد» وCPA يخص مسار المبيعات فقط؛ «صفر زيارات» يخص مسار الزيارات فقط وبشروط حد العينة والإنفاق والحالة النشطة.

## 3 — المالية التشغيلية: الرحلة الواقعية غير المكررة
**خدمة لعميل وكالة ضمن Tenant، وليس اشتراك مالك SaaS.** لا تخلطها مع `platform_registration` أو مدفوعات اشتراك CampaignsHub أو فواتير مالك المنصة.

### أ. من طلب الحملة حتى التشغيل دون انتظار مشروع
1. **مدير المشاريع** ينشئ `طلب حملة` من صندوق العمليات ويحدد عميلًا موجودًا أو مسودة عميل جديد، عنوان المشروع، القنوات والهدف، الميزانية المبدئية، العملة، الفترة، المسؤول، والمرفقات/عرض السعر. إنشاء الطلب **لا يحتاج مشروعًا مُسبقًا** ولا ينشئ عميلًا/مشروعًا مكررًا.
2. **عرض السعر** يستخدم محرك العروض الموجود إذا مناسب مع reference، ويُرسل للعميل أو يُعتمد وفق سياسة الوكالة. لا تصف «العميل وافق» حتى وجود موافقة فعلية أو مستند موثق.
3. **العميل** يحول المبلغ إلى حساب الشركة ويرسل الإيصال عبر البوابة أو يرفعه مدير المشروع نيابة عنه مع نسبة المصدر؛ رفع الإيصال = `بانتظار مطابقة` وليس `تم الاستلام`.
4. **المالية** تتلقى صندوق عمل باسم واضح، وترى: العميل، الطلب، عرض السعر، قيمة التحويل، الإيصال، المرجع، تاريخ العملية، طريقة الدفع؛ تطابق مع كشف البنك/مصدر تحصيل موثوق، وترفض/تطلب استكمال/تعتمد. **لا تتحقق تلقائيًا من صحة التحويل لمجرد OCR أو إيصال PDF**.
5. بعد الاعتماد تُسجل **حركة تمويل** فريدة قابلة للتدقيق، ويُثبت المشروع أو يُربط بمشروع قائم بطلب واضح. يظهر «الرصيد متاح» لفريق الحملات، مع إمكان ربط الحسابات الإعلانية وبدء إطلاق الحملات ضمن الصلاحيات. تخطيط الحملات قبل الدفع ممكن؛ **الإطلاق الفعلي** يخضع لسياسة التشغيل والاعتماد، وليس لمجرد وجود مسودة.
6. فريق الحملات يربط الحساب/الحسابات المختارة فقط بالمشروع، ويميز الحسابات `ضمن التمويل المسبق` أو `خارج التمويل` أو `دفع مباشر/آجل`؛ لا يجمع إنفاق منصة أخرى في رصيد العميل.
7. المحاسب مسؤول عن إثبات الاستلام والتسويات، ومدير المشروع مسؤول التواصل والتجديد، ومسؤول الحملات مسؤول التشغيل وربط الإنفاق. **هذا توزيع أدوار عملي، وليس حكمًا قانونيًا بإعفاء أي شخص من التزاماته الوظيفية**؛ يظل سجل الاعتمادات والأحداث دليلًا على الإجراءات.

### ب. الإضافات والتجديدات
- زر **«زيادة الميزانية»** من المالية وصفحة العميل. يدخل مبلغًا ومصدر تمويل وتاريخًا ومرجعًا وإثباتًا، مع كشف الرصيد قبل/بعد؛ عند الاعتماد **يُضاف إلى الرصيد الحالي** ويبقى الإنفاق السابق. لا تبدأ ميزانية أخرى بلا علاقة ولا تعيد ضبط الحساب.
- السجل المحاسبي: تمويل أولي + كل تجديد + إنفاق يومي حقيقي قابل للخصم + تسويات/عكس معتمدة. **الدفتر append-only للأحداث المعتمدة**؛ حقائق الإنفاق اليومية قابلة للتحديث على أساس المفتاح الفريد مع ledger للأثر التفاضلي، ولا تعيد خصم نفس اليوم عند sync/reconnect.
- مبلغ تمويل أولي 41,250 ر.س، إنفاق 30,711 ر.س، متبقي 10,539 ر.س؛ تجديد 20,000 → الإجمالي 61,250 والمتبقي 30,539، ولا يتغير الإنفاق. هذا المثال معيار قبول لا رصيد Production معتمد.
- يجب توضيح حالة أرصدة **مسبقة/مباشرة/آجلة**، وعدم خصم إنفاق خارج التمويل أو قبل تاريخ الرصيد الافتتاحي. يظل لكل عميل عدة مشاريع عند الحاجة، ويمكن تحديد نسبة/توزيع التمويل بالمشروع أو على مستوى العميل بتصريح واضح دون مضاعفة.

### ج. تحويل الميزانيات والإنفاق إلى SAR
- العملة الموحّدة **للعرض والتجميع التشغيلي** SAR (`ر.س`)، مع عرض original amount/currency ورقم المصدر. **لا تغيّر عملة الحملات أو المنصات ولا أسعار ميزانياتها الحية**.
- التحويل اليومي وفق سعر صرف موثق ومؤرخ ليوم fact، مع مصدر السعر، وإذا rate غير موجود فلا تقدّر رقمًا ولا تُظهر إنفاقًا ناقصًا كمجموع مكتمل. `USD→SAR 3.75` عبر الربط الرسمي المدعوم في الكود، وأي عملة عائمة تعتمد بيانات تاريخية موثوقة؛ دعم backfill بعد موافقة.
- لا تخلط budget plan/monitoring limit/actual client funds/invoices مع بعض. تظهر كلها بأسماء واضحة في drill-down؛ الحساب الرئيس للمتبقي = المعتمد المسبق − الإنفاق المؤهل ± التسويات.

- **عند اختيار العميل:** اللوحة تبقى نفسها وتعرض تفصيل تمويل المشروع، الدفعات، المنصات، الحسابات الإعلانية، الحملات، الرصيد والرسم وسجل التدقيق في drawer/توسيع سياقي. لا تختزل بيانات التدقيق بسبب التصميم الكثيف.
- **على الجوال 320–430px:** 2×2 المؤشرات المختصرة، شريط «يحتاج إجراءك»، خط الرصيد بعرض الشاشة، بطاقات العملاء الأولى مع الرصيد وزر «زيادة/متابعة»، تفاصيل في شاشة فرعية أو bottom sheet. **بلا تمرير أفقي للصفحة**؛ البطاقات والحواف والأزرار تدعم اللمس ولوحة المفاتيح.

**حالات خاصة:** الدفعات قيد المطابقة لا تُضاف ضمن المعتمد، المتبقي السالب يظهر سالبًا مع حالة واضحة، إيقاف مزامنة يذكر آخر تاريخ فعلي، واختلاف العملات يُظهر coverage بدل رقم «آمن» ناقص.

### هـ. تنبيهات استباقية بدون تحميل التسويق مسؤولية المالية

## ج. النموذج التجاري والتنظيم الصحيح
**مالك المنصة** لديه بوابة إدارة عامة (ليست Tenant وكالة): الرئيسية، التسجيلات، الطلبات، المساحات، المشتركين، الباقات، الخدمات، المدفوعات، الدعم، التشغيل، الإعدادات.
- `التسجيلات`: المتقدمون لشراء Solo/Team/Agency/Enterprise، والمراجعة والتحقق والدفع/الإعفاء وإنشاء Tenant مرة واحدة.
- `الطلبات`: جميع **خدمات مالك CampaignsHub** من `campaignshub.io/#services`، بما فيها إدارة الإعلانات والمؤثرين وUGC وأي خدمة منشورة؛ لكل طلب نوع، مسؤول، حالة، مرجع، متابعة، تحويل وتاريخ نشاط. لا تعتبر الطلب اشتراكًا تلقائيًا.
- `المساحات`: حدود العزل والحالة والعضويات والتكاملات. `المشتركين`: علاقة العميل التجاري بالاشتراك/الفوترة، وليسا قائمتين مكررتين إذا كان المحتوى واحدًا.
- طلبات وكالة مشتركة عبر نطاقها أو بوابتها ملك Tenant الوكالة، وليست من خدمات مالك المنصة.
- نموذج المهتمين أو lead ad ملك Tenant/Client/Project، وليس طلب خدمات أو تسجيل SaaS.
- **طلب خدمة مؤثرين من موقع المنصة** يبدأ في Platform Service Inbox؛ لا يتحول لترشيح/تعاون في Tenant دون قرار وتحويل مرجعي واضح.
- ClientWorkspace يملك Project واحدًا أو أكثر؛ يخفي المشروع الوحيد بصريًا، ولا تُمحى علاقته. كل عميل يحصل على بوابة دعوات مستقلة والصلاحيات backend.

**القائمة المعتمدة لمساحة وكالة:** الرئيسية؛ الحملات (الحملات، المحتوى)؛ النتائج (التحليلات، التقارير، المهتمين)؛ المالية (الميزانيات، الفواتير)؛ العمليات (العملاء، الطلبات، التنبيهات، المهام، الأتمتة)؛ الإعدادات (التكاملات، الفريق، الصلاحيات، الاشتراك، الحساب). 
**Solo:** الرئيسية، الحملات، المحتوى، التحليلات، التقارير، المهتمين، الميزانيات، التنبيهات، الإعدادات وفق الباقة.
**بوابة العميل:** الرئيسية/الأداء، الحملات، التقارير، الطلبات، المحادثات، الفواتير، الاعتمادات فقط بما تسمح به الوكالة.
**وحدة المؤثرين:** التعاونات، المؤثرين، الترشيحات، المخرجات، الأثر؛ دعوة المؤثر إلى أعماله فقط.

**تصحيح للمهمة 12 في الملحق الأصلي:** لا تجعل «العملاء» رابطًا مستقلًا أعلى قائمة الوكالة؛ اجعله تحت «العمليات»، وأظهر «الطلبات» رابطًا مستقلًا هناك (مع الطلبات الخاصة بكل عميل داخله أيضًا). القائمة الرئيسية للمالك Super Admin مختلفة تمامًا.
**تصحيح للمهمة 7:** «طلبات العملاء» تبويب ضمن «العملاء»، مع صندوق «الطلبات» داخل «العمليات» للتتبع الشامل، لنفس السجل لا نسختين.
**تصحيح للمهمة 6:** تجربة «عميل جديد» واحدة، مع مشروع أول قائم داخليًا، والسماح بعدة مشاريع عند الحاجة. لا تعيد رسم جداول DB ولا تغيّر المسارات القديمة لتعديل شكلي فقط.

## د. فحص الأمن وملكية الطلبات — أول أولوية إذا ظهرت فجوة
- أثبت رحلة الزائر `campaignshub.io/#services` → زر الخدمة → المسار العام → API → controller → record → owner scope → inbox → المسؤول/الإشعار. **لا تفترض أن `PortalTenantResolver` يجعل طلب خدمة المنصة Platform-owned؛ افحص المسار الحقيقي.**
- عيّن الجهة المالكة في الخادم وفق نطاق/سياق موثوق، لا `tenant_id` من المتصفح ولا tenant افتراضي. مجهول الملكية يرفض بصورة آمنة مع trace.
- افصل طلبات Platform عن Tenant/client requests/lead submissions في التخزين أو الإسقاط والصلاحيات، دون تكرار أو نقل بيانات قديمة غير مثبتة.
- راجع كل cross-tenant IDOR: API، صفحات، تقارير، بحث، إجماليات، إشعارات، files، exports، cache، jobs، webhooks.
- وثّق التدقيق على الإنشاء/الاعتماد/التحويل والتغييرات المالية. لا تختبر مدفوعات أو رسائل فعلية دون إذن. اعتمد تفاصيل فحوص S01–S22 في الملحق الأمني.

## هـ. منطق النتائج والتنبيهات — لا أحكام خاطئة
- هدف الحملة يحدد «النتيجة»: وعي وصول/ظهور، زيارات **LPV عند توفره وإلا النقرات مع تسميتها صراحةً «نقرات»**، تفاعل/مشاهدات، مهتمين نماذج/أحداث مؤهلة، مبيعات شراء/إيراد/ROAS، تطبيقات تثبيت. لا تستخدم مجموعًا واحدًا لمؤشرات أهداف مختلفة.
- قارن نطاقًا وفترة متكافئين، وأظهر سبب غياب البيانات عند نقص المقاييس. لا تُحوّل نتائج زيارات إلى «0 شراء» أو «صرف بدون نتائج».
- **الحملات النشطة وحدها** مؤهلة لتنبيهات الأداء مع إنفاق حديث وحد عينة؛ الحملة المنتهية/الموقوفة/المنتهية ميزانيتها لا تُرسل لها إنذار عائد أو تكلفة على أنه مشكلة أداء، بل حالة ميزانية أو ملخص محايد عند انطباق الشرط.
- تنبيه «33.59× إلى 1.08×» لحملة Ettifaq المنتهية يجب ألا يصدر كإنذار تراجع حي، مع الحفاظ على الأداء التاريخي العالي مرئيًا دون مبالغة؛ حملة 1KCOFFEE هدفها زيارات فتظهر زياراتها الفعلية.
- كل تنبيه: **ماذا حدث + احتمال مؤسس على بيانات (لا تشخيص مؤكد بلا إثبات) + خطوة تالية قابلة للتنفيذ**.
- حد الإنفاق للمتابعة والتنبيه لا يعني أن النظام لا يمتلك أتمتة؛ استخدم: **«هذا الحد للمتابعة والتنبيه. للإيقاف التلقائي فعّل قاعدة من الأتمتة.»** إذا كان الإيقاف الآلي متاحًا ومفعلًا؛ لا توهم المستخدم بوجود إيقاف إذا لم يثبت تنفيذه.

## و. اللهجة ودليل الأسلوب — شرط قبول أفقي لكل دفعة
**طبق جميع بدائل القاموس الأصلي حرفيًا على واجهات الوكالة وSolo وبوابة العميل وإدارة المنصة والطلبات ورسائل البريد والتنبيهات والتقارير والمشاركات والتصدير.** السعودية البيضاء الاحترافية: جمل قصيرة، أفعال وأزرار واضحة، لا فصحى معقدة ولا اتهام. أمثلة مرجعية:
- «من أين جاءت النقرات» ← **«مصادر الزيارات»** عندما يكون المصدر يقيس زيارات فعلًا؛ عند قياس clicks فقط استخدم «مصادر النقرات»، ولا تضلّل في معنى المؤشر.
- «العتبة» ← «الحد»؛ «المستهلك/المصروف/المنصرف» في سياق ميزانية الحملات ← «الإنفاق»؛ «المحفظة» ← «ملخص المشاريع»؛ «الإبداعات» ← «المحتوى/المحتويات»؛ «العملاء المحتملون الأصليون» ← «المهتمين».
- «اقترب الإنفاق من الحد الذي وضعته» ← **«قرّبت تخلص ميزانية الحملات»** أو «قرّبت تنتهي ميزانية الحملات» بحسب السياق؛ لا تعمم وصفًا لا ينطبق على حساب آخر.
- «إنفاق بلا نتائج» ← «صرف بدون نتائج» **فقط إذا ثبت أن نتيجة الحملة المعرّفة صفر فعليًا بعد حد بيانات مناسب**.
- «النتائج المُبلّغة» ← «النتائج» مع إظهار تاريخ ومصدر البيانات بشكل متاح.
- العائد على الإنفاق (ROAS) لحملات المبيعات فقط. حرف لاتيني كبير في الاختصارات، أرقام 1/2/3، عملة ر.س؛ عند الضرورة للحسابات الأجنبية وضح العملة الفعلية قبل التحويل.
- العناوين المختصرة والرسوم قبل النص **ما دام الرسم صادقًا ومعنى البيانات مفهومًا**؛ أظهر الجداول حين تكون أنسب. أخضر=أفضل/أحمر=أسوأ حسب سياق المؤشر، مع أيقونة أو نص للحالة وعدم الاعتماد على اللون وحده.
- لا تنقل كل نصوص الواجهة والـbackend والبريد إلى ملف ترجمة تقني واحد يخرّب architecture؛ وحد قاموس المصطلحات والتخطيط حسب الأنظمة الحالية مع اختبار AR/EN وRTL/LTR.
- في الرسائل القانونية والأمنية والفوترة استخدم لغة احترافية دقيقة حتى لو كانت أبسط من النص الحالي.
- أصلح النصوص القديمة ضمن **دفعات محدودة** وطبّق الأسلوب فورًا على كل كود جديد. لا تعتبر دليل الأسلوب أمرًا ثانويًا أو «طلبًا إضافيًا».

## ز. تجربة الوكالة والعملاء والمالية
- مساحة Smart Code قد تضم حتى 30 عميلًا/مشروعًا نشطًا؛ **ملخص كل العملاء** يجمع الإنفاق على أساس العملة ومصادر الإنفاق ذاتها، ولا يجمع نتائج أهداف مختلفة في رقم واحد.
- مدير المشروع يرى ويُراسل عملاءه المصرح بهم فقط؛ صلاحيات قابلة للضبط على مستوى صفحة/فعل، وتحفظ Backend enforcement. العميل يدخل عبر دعوة من صفحة العميل لا عبر عضوية الوكالة.
- الميزانية/الإنفاق/المتبقي لكل عميل، وتوزيع الحسابات والفترة وسعر الصرف التاريخي؛ لا تخلط «حد الإنفاق» الإداري مع الرصيد المعتمد من المالية.
- قاعدة الإنفاق اليومية قابلة لتحديث fact لنفس الحساب واليوم؛ سجل اعتماد الميزانية والتسويات المالية يحتفظ بأثر تدقيق لا تعديل صامت. حل تعارض «append-only vs replace on re-sync» في التصميم قبل أي migration.
- البريد اليومي 8 صباحًا بتوقيت الرياض: نسخة كل عميل/مشروع ونظرة 7 أيام لكل منصة ومقارنة أمس، ونسخة «ملخص المشاريع» موحدة؛ كل مدخل يُظهر **هدفه الفعلي** وتوصية استرشادية لا اتهامًا لأداء الفريق. إرسال البريد الفعلي يثبت بحالة المزود، لا القالب.
- تجربة الحفظ: زر يظهر الحالة، رسالة نجاح **بعد commit فقط**، تحديث البيانات تلقائي، خروج/عودة منطقية، وخطأ مفصل دون فقد مدخلات.

- **لا تدّعِ 100% مطابقة** إذا API LinkedIn/X لا يقدم محتوى معينًا أو credentials/scope غير معتمد؛ سجل التغطية الحقيقية وما يتعذر مع السبب وحالة `BLOCKED_EXTERNAL_CREDENTIALS` عند الحاجة، وأظهر placeholders واضحة، لا وسائط وهمية. لا تعدّل سناب/تيك توك/ميتا/جوجل دون سبب مثبت.
- **تقرير الرابط والمحفوظ والتصدير** تستخدم تعريفًا واحدًا لإعدادات الأهداف والمؤشرات وما يمكن فتحه، مع وضوح الاختلاف بين snapshot محفوظ وlive. خيارات `تشغيل الفيديو/تكبير الصور/تحميل الأصل/مقارنة الإعلانات/النص والعنوان/CTA/الإنفاق/الإيراد/تكلفة الطلب/ROAS/التحليلات/التوصيات` يجب أن تُختبر option-by-option في كل وسيط مدعوم.
- **الأصل لا يُكشف** إذا الخيار يخفي الرابط؛ لكن إخفاء زر من واجهة عامة لا يكفي لضمان منع URL مباشر: طبّق صلاحية الخادم/توقيع الملف حيث يلزم، بلا كسر المشاركة الموجودة.
- **PDF والتقديم**: استخدم 16:9 للشرائح عند اختيار العرض التقديمي، وتخطيطًا متجاوبًا لصفحات PDF المطولة دون قص محتوى أو هوامش زائدة؛ لا تفرض أحجامًا متغيرة تؤدي لملفات غير قابلة للعرض.

## المهمة 1: هدف الحملة يحدد «النتائج»
- لكل حملة هدف (وعي / زيارات / تفاعل / مهتمين / مبيعات / تطبيقات) يُقرأ من المنصة ويُعدّل يدوياً.
- جدول مركزي واحد يربط الهدف بالنتيجة ومؤشراتها:
  - وعي = الوصول والظهور وCPM
  - زيارات = زيارات الصفحة LPV (أو النقرات)
  - تفاعل = التفاعلات والمشاهدات
  - مهتمين = النماذج + أحداث صفحة الهبوط (مهتمين الهبوط)
  - مبيعات = المشتريات والإيراد وROAS وتكلفة الطلب
  - تطبيقات = التثبيتات
- هذا الجدول هو المصدر الوحيد لكلمة «النتائج» في اللوحات والتقارير والتنبيهات والملخصات والأتمتة.
- الحملات بأهداف مختلفة تُعرض كل واحدة بنتيجتها. لا تجمع أهدافاً مختلفة في رقم واحد، ولا تستبعد حملة لأن هدفها مختلف إلا إذا استبعدتها يدوياً.

معيار القبول: حملة «2Nov 2026 ــ Branches ــ Combo ــ IG Post» (زيارات) تظهر نتيجتها زيارات لا «0 نتائج».

## المهمة 2: منطق التنبيهات
- تنبيهات الأداء (العائد، تكلفة النتيجة، صرف بدون نتائج) فقط لحملة شغالة صرفت آخر 24 ساعة.
- الحملة المنتهية أو الموقوفة أو التي وصلت حدها = تنبيه ميزانية فقط: «خلصت ميزانية الحملة» + ملخص نتيجتها + خيار التجديد.
- العائد يُقيّم لحملات المبيعات فقط، والمقارنة بين أيام متساوية النشاط وبحد أدنى للإنفاق.
- كل تنبيه = ماذا حدث + السبب المحتمل + الحل المقترح (محتوى / استهداف / ميزانية / صفحة هبوط / تتبع). ممنوع تنبيه بلا حل.
- صياغة محايدة تبدأ بالإيجابي إن وجد (مثل: العائد التراكمي 33×). ممنوع «ضعيف» و«فشل» و«قصور». الإيميل لا يصير وثيقة تدين مدير الحملات.
- أغلق تلقائياً تنبيهات الأداء المفتوحة على حملات منتهية (migration لمرة واحدة).

معيار القبول: لا يظهر تنبيه «العائد تراجع من 33.59× إلى 1.08×» لحملة «29Oct 2026 Ettifaq vs Ajman» المنتهية، ولا «صرف بدون نتائج» لحملة 1KCOFFEE (زيارات).

## المهمة 3: إدارة قواعد التنبيه
- القواعد الحالية لا تُعدّل ولا تُوقف (الـAPI فيه GET وPOST فقط). أضف PATCH وDELETE لـ /api/v1/alerts/rules/{id}، وفي الشاشة: تعديل وإيقاف وحذف.
- لكل قاعدة: الاسم، الحد، الخطورة، المدة بين التنبيهات، القنوات، المستلمون (إيميلات أو «مدير المشروع» تلقائياً).
- بعد الحفظ: رسالة «تم الحفظ» وتحديث فوري.

## المهمة 4: اللهجة والمصطلحات
- اجمع كل النصوص العربية في ملف ترجمة واحد (الواجهة، البريد، التنبيهات، التقارير، الملخصات).
- طبّق «دليل الأسلوب» في آخر الملف حرفياً في كل مكان.
- اكتب لي ملفاً بكل نص تغيّر (قبل ← بعد).

معيار القبول: البحث عن (العتبة، المستهلك، المحفظة، الأصليون، الإبداعات، المنصرف، المصروف) يرجع صفر نتيجة في النصوص المعروضة.

## المهمة 5: الحفظ يظهر ويتحدث
- كل زر حفظ/إنشاء/تعديل/حذف: الزر يتعطل أثناء الحفظ ← رسالة «تم الحفظ» أو سبب الخطأ بالعربي ← تحديث البيانات فوراً ← الرجوع أو إغلاق النافذة.
- استبدل كل window.prompt وwindow.confirm بنوافذ داخل النظام.
- مكوّن مشترك واحد للجميع.

## المهمة 6: العميل هو الوحدة الظاهرة
- «عميل جديد» = نموذج واحد (الاسم، العملة، مدير المشروع) ينشئ العميل + مشروعه الداخلي + بوابته.
- الفلتر العلوي قائمة عملاء واحدة مع بحث. صفحة «المشاريع» تندمج في «العملاء».
- المشروع مخفي افتراضياً، ويظهر محوّل «المشاريع» داخل صفحة العميل فقط إذا أُضيف له مشروع ثانٍ. عزل البيانات بين المشاريع لا يتغير.
- لا تغيّر أي ID أو مسار API. الروابط القديمة (/agency/projects/...) تحوّل لصفحة العميل.

## المهمة 7: الفريق والصلاحيات وبوابة العميل
- أدوار جاهزة قابلة للتعديل بمربعات اختيار (أي صفحة تظهر وأي إجراء مسموح):
  - مدير المساحة: كل شيء.
  - مدير مشروع: عملاؤه فقط في كل مكان.
  - المالية: الرئيسية للقراءة + قسم المالية لكل العملاء. يضيف الميزانيات. لا يرى الحملات والمحتوى والإعدادات.
  - مشتري إعلانات، محلل، معدّ تقارير، مطّلع.
- إعدادات العميل > «البوابة»: أكتب إيميل العميل، أختار (مطّلع/معتمِد)، فيوصله بريد دعوة بالعربي يدخله لبوابته مباشرة، ولا يرى المساحة أو أي عميل آخر.
- بوابة العميل فيها 3 أقسام: الأداء، بانتظار اعتمادك (المحتوى)، طلباتي.
- طلبات العميل ومحادثاته تظهر في صفحة العميل وفي «العمليات > طلبات العملاء»، ويوصل إشعار لمدير المشروع. حالات الطلب: جديد / قيد التنفيذ / تم، ويراها العميل في بوابته بشريط من 3 مراحل.
- في صفحة الفريق أرى من يتابع كل عميل، والعميل بلا مدير مشروع يظهر بعلامة.

## المهمة 8: بريد يومي لكل عميل (8:00ص بتوقيت الرياض)
- رأس: اسم العميل + هدف الحملات + الميزانية والإنفاق والمتبقي بشريط.
- مؤشرات آخر 7 أيام (الإنفاق، النتيجة حسب الهدف، تكلفتها، المؤشر الثاني) بخط صغير ومقارنة بأمس وبالأسبوع السابق.
- صف لكل منصة بنفس المؤشرات ومقارنة بأمس، أفضل 3 حملات، «نقاط تحتاج انتباه» (الملاحظة + الحل).
- سطر ثابت: «الأرقام من المنصات كما أبلغت بها، والتوصيات استرشادية وتخضع لقرار فريق إدارة الحملات.»
- رسوم PNG مولّدة على الخادم، RTL، يعمل في Gmail وOutlook والجوال. زر «أرسل نسخة تجريبية لي».
- يصل لي ولمدير مشروع العميل. الهدف: البريد يغنيني عن الدخول لكل منصة ولكل عميل.

## المهمة 9: بريد يومي واحد «ملخص المشاريع»
- إجماليات كل العملاء آخر 7 أيام (نتائج حسب كل هدف) + خط الإنفاق اليومي.
- صف لكل عميل: الإنفاق، النتيجة باسم هدفها، التغير عن أمس، المتبقي بشريط.
- «تنبيهات ومهام اليوم»: أهم 5، كل واحدة = الملاحظة + الحل + رابط.
- نفس قواعد المهمة 8.

معيار القبول: مجموع صفوف العملاء = الإجمالي في الأعلى.

## المهمة 10: التقارير
- إعدادات التقرير schema واحد يقرؤه: الرابط والمحفوظ والتصدير. أي خيار في واحد موجود بنفس الأثر في البقية.
- «هدف التقرير (قالب القياس)» و«المؤشرات المعروضة» يعملان في تقرير الرابط أيضاً. الهدف يقبل أكثر من هدف، وافتراضياً من أهداف الحملات (المهمة 1).
- قسم «ما يمكن فتحه» للإعلانات (تشغيل الفيديو، تكبير الصور، تحميل الأصل، مقارنة الإعلانات، نص الإعلان، الأرقام، التحليل):
  - اكتب اختباراً لكل خيار أولاً، ثم أصلحه.
  - المخفي يختفي 100%، والمعروض يظهر بغلافه.
  - لا تغيّر طريقة عرض المحتويات الحالية.
- العرض التقديمي وPDF: كل صفحة بحجم محتواها بالضبط، بلا هوامش أو فراغات (مثل شرائح 16:9).

معيار القبول: نفس التقرير بهدف «زيارات + مبيعات» يظهر بنفس المؤشرات والأرقام في الرابط والمحفوظ وPDF.

## المهمة 11: محتويات X ولينكدإن لا تظهر

معيار القبول: عدد الإعلانات في التقرير = عددها في مدير الإعلانات لنفس الفترة، وكلها بصورها.

- ثم خطة دفعات صغيرة: لكل دفعة ما يتغير، والروابط القديمة وأين تحوّل، وكيف أتحقق. توقف وانتظر موافقتي.

- أسماء قصيرة بدون ابتكار أسماء جديدة غير المذكورة.
- لا حذف لأي وظيفة، ولا تغيير IDs أو API أو الروابط.
- كل ميزة تُوصل بنقرتين بحد أقصى، وكل رابط قديم يحوّل للجديد.
- توافق العربية والإنجليزية وRTL/LTR والجوال.

## المهمة 13: «الرئيسية» واحدة بمستويين لكل البوابات
- مكوّن واحد OverviewDashboard:
  - «كل العملاء» (الوكالة فقط، الافتراضي).
  - «عميل واحد» (نفس لوحة /app/dashboard الحالية). يفتح بالضغط على بطاقة العميل، ومسار «كل العملاء › اسم العميل» يرجع.
- كل العملاء:
  - 4 أرقام: الإنفاق، المتبقي، عملاء شغالين، قرّبت تخلص.
  - خط الإنفاق اليومي، ودائرة توزيع الإنفاق حسب المنصة.
  - بطاقات العملاء: حلقة الميزانية + خط 7 أيام + «تكفي N يوم»، مرتبة: الأقرب للنفاد أولاً، ثم من عنده تنبيهات أو مهام، ثم الأكثر إنفاقاً.
- عميل واحد: المؤشرات حسب الهدف، الخط اليومي، دائرة المنصات، قمع رحلة العميل، رسم أسباب التغيّر.
- المنطق: العملات تُحوّل للريال، لا جمع للأهداف، المقارنة فقط للبيانات المكتملة، مجموع البطاقات = الإجمالي.
- نفس المكوّن في بوابة المعلن وبوابة العميل الخارجية (بدون أزرار الإدارة). ممنوع نسخ الكود لكل بوابة.

## المهمة 14: الباقات (بوابة واحدة)
- بوابة واحدة لكل الباقات. الباقة تحدد الحدود والمزايا الظاهرة، والدور يحدد المسموح منها.
- الحدود تُقرأ من لوحة الإدارة (لا أرقام داخل الكود).
- المزايا:
  - Solo = الأساس + التنبيهات + الميزانيات + البريد اليومي.
  - Team = + الفريق + بوابة العميل + التقارير المجدولة ومتعددة العملاء + الذكاء.
  - Agency = + الأتمتة المتقدمة والوكلاء + العلامة البيضاء.
- الترقية في نفس البوابة بدون تسجيل خروج: Solo ← Team تظهر «العملاء» و«كل العملاء» والفريق فوراً.
- النزول مسموح فقط إذا الاستخدام داخل حدود الباقة الأصغر، والبيانات المقفلة تبقى محفوظة.
- الميزة غير المشمولة تظهر بقفل واسم الباقة، والنقر يفتح مقارنة الباقات.
- تنبيه عند 75% و90%، وعند 100% يُمنع الجديد فقط ولا يتوقف شيء شغال.
- مستخدمو بوابة العميل لا يُحسبون من مقاعد الفريق.
- صفحة الاشتراك: حلقة لكل حد (المستخدم/الحد) + بطاقات الباقات.

## المهمة 15: مدير المشروع
- دور «مدير مشروع» أختار له عملاءه. يرى عملاءه فقط في كل مكان (القائمة، البحث، الإجماليات، التنبيهات).
- بريد يومي 8:00ص لعملائه: المتبقي بالريال و«تكفي N يوم» + أداء أمس مقابل آخر 7 أيام.
- تنبيه عند 75% و90% و100% من ميزانية العميل، ليتابع التجديد مع العميل.

## المهمة 16: المالية — الميزانية والإنفاق والمتبقي

الهدف: الإجابة في ثانية عن «كم الميزانية، كم الإنفاق، كم المتبقي لكل عميل».

دورة العمل (كما في الوكالة):
1. العميل يحوّل الميزانية ← المحاسب (دور المالية) يدخل «إضافة ميزانية»: يختار العميل والمبلغ والتاريخ وملاحظة.
2. المبلغ ينضاف فوراً لإجمالي ميزانية العميل ويرتفع المتبقي.
3. إدارة الحملات تطلق الحملة وتربط المنصة.
4. الإنفاق اليومي من كل المنصات المربوطة يُخصم تلقائياً من المتبقي.
5. عند 75% و90% و100% تنبيه لمدير المشروع والمالية للتجديد.

الدفتر:
- لكل عميل حركات: ميزانية (+)، إنفاق يومي من كل المنصات المربوطة (−)، تسوية (±).
- المتبقي = الميزانية − الإنفاق ± التسويات، منذ البداية. بدون فترات، فلا تداخل ولا تراكم.
- مفتاح فريد (العميل + الحساب الإعلاني + اليوم): إعادة المزامنة تستبدل نفس السطر ولا تكرره.
- لا يُخصم إنفاق قبل تاريخ أول ميزانية.
- العملة: الدفتر بالريال، والحسابات بعملة أخرى تُحوّل بسعر يومها مع حفظ المبلغ الأصلي.
- منصة تُدفع خارج ميزانية العميل: تُعلَّم «خارج الميزانية» فلا تُخصم وتظهر منفصلة.
- كل حركة مسجلة باسم من أدخلها وتاريخها، ولا تُحذف (تُعكس بتسوية).
- نموذج التمويل لكل عميل: مسبق / مباشر / لاحق. المسبق فقط يدخل في إجمالي المتبقي.

صفحة «المالية > الميزانيات» (بسيطة، رسوم قبل النص):
- **الدورة:** 4 دوائر بأيقونات وأرقام: الميزانية ← الإطلاق ← الإنفاق ← المتبقي.
- **3 أرقام كبيرة:** الميزانية، الإنفاق، المتبقي (لكل العملاء).
- **تبويب «الأرصدة»:** صف لكل عميل = شريط ملوّن بإنفاق كل منصة + جزء أخضر للمتبقي، وبجانبه 3 أعمدة: الميزانية | الإنفاق | المتبقي. مرتب من الأقرب للنفاد، والمتجاوز بالأحمر.
- **تبويب «إضافة ميزانية»:** أزرار لاختيار العميل + أزرار مبالغ سريعة (5,000 / 10,000 / 20,000 / 50,000) أو مبلغ مخصص + زر «أضف [المبلغ] ريال إلى [العميل]»، وتحتها بطاقات آخر الإضافات.
- **تبويب «التسويات»:** استرداد، إضافة، شطب، تصحيح إنفاق، تصحيح إيراد. لا تُطبق إلا باعتماد شخص غير من أنشأها.
- صفحة العميل > تبويب «الرصيد»: حلقة كبيرة + الميزانية والإنفاق والمتبقي + سجل الحركات + «إصدار كشف» PDF يثبّت الرصيد بتاريخه ويمكن إظهاره في بوابة العميل.

يظهر المتبقي في: بطاقة العميل في الرئيسية، رأس صفحة العميل، بريد مدير المشروع، بوابة العميل.

بريد يومي 8:00ص للمالية: الإجماليات، الأقرب للنفاد، من يحتاج تجديد خلال 7 أيام، التسويات بانتظار الاعتماد.

نص الحد الموحد: «هذا الحد للمتابعة والتنبيه. للإيقاف التلقائي فعّل قاعدة من الأتمتة.» مع زر ينشئ قاعدة إيقاف مرتبطة بالمتبقي.

الانتقال من نظام مؤشر:
- استيراد CSV لكل عميل: نموذج التمويل، الميزانيات (المبلغ، التاريخ، الملاحظة)، التسويات المعتمدة.
- أو رصيد افتتاحي بتاريخ محدد، والإنفاق يُخصم من اليوم التالي فقط.
- إذا اختلف المتبقي عن مؤشر بأكثر من 1% يظهر فرق المطابقة لكل منصة.

ممنوع: حذف أي حركة، أو تعديل حدود الإنفاق الحالية تلقائياً.

معيار القبول:
- نادي الإتفاق: ميزانيات 41,250 (10,000 + 7,500 + 3,750 + 20,000) وإنفاق 30,711 ← المتبقي 10,539 مطابق لمؤشر.
- المحاسب يضيف 20,000 ← المتبقي يصير 30,539 فوراً، وبعد مزامنة الإنفاق يُخصم تلقائياً.
- إعادة مزامنة نفس اليوم لا تغيّر الرقم.
- مستخدم بدور «المالية» يرى المالية لكل العملاء ولا يرى الحملات.

# CampaignsHub — العقد الهيكلي والأمني ومسارات الطلبات

## 0. الهدف ومصادر الحقيقة

**CampaignsHub منصة SaaS متعددة المستأجرين** لإدارة الحملات الإعلانية المدفوعة، والتكاملات والمتاجر، والتحليلات، والتقارير التفاعلية القابلة للمشاركة، مع خدمات أخرى يقدمها مالك المنصة. **مالك المنصة (Super Admin) ليس وكالة مشتركة؛ ولا يجوز معاملة مساحته أو طلبات خدماته العامة كبيانات أي مستأجر.**

ترتيب الحقيقة عند التعارض:
1. Git الحالي (`origin/main`)، الـPRs وCI وDeploy وسلوك Production الموثق.
2. `docs/REQUIREMENTS_TRACEABILITY_MATRIX.md` وسجل العيوب و`docs/RESUME_STATE.md`.
3. المتطلبات الدائمة وملفات تسليم المشروع وملف التنفيذ التراكمي وملف منصة التكاملات الموحدة.
4. هذا الملف مرجع لتصحيح **الهيكل والملكية والحدود**؛ لا يمحو ما قبله ولا يعيد تنفيذ VERIFIED.

**حالات التنفيذ الإلزامية:** `NOT_STARTED`، `IN_PROGRESS`، `PARTIAL`، `IMPLEMENTED_NOT_VERIFIED`، `VERIFIED`، `BLOCKED_EXTERNAL_CREDENTIALS`، `BLOCKED_OPERATIONAL_EVIDENCE`. لا يصح استبدالها بعبارة عامة «مكتمل».

## 1. الطبقات والكيانات: لا تخلط صلاحياتها

```text
CampaignsHub.io (الموقع العام / التسويق / الأسعار / الخدمات)
│
├── طلب اشتراك SaaS ──> نطاق إدارة المنصة (Platform Registration)
│                            └── مراجعة / تحقق / قرار / دفع مثبت / إنشاء مساحة
│
├── طلب خدمة مقدمة من CampaignsHub ──> صندوق خدمات مالك المنصة
│                                         └── مسؤول / عرض / تعاقد / تنفيذ / إغلاق
│
├── وصول المستخدمين الحاليين
│   ├── إدارة المنصة Super Admin [عبر بوابة منصة مستقلة؛ بلا tenant membership]
│   ├── مساحة Solo / مستقل / معلن [Tenant]
│   └── مساحة Team / Agency [Tenant]
│        ├── العميل ClientWorkspace A
│        │    ├── مشروع 1 [ربط الموارد والحملات والبيانات]
│        │    ├── مشروع 2 [اختياري؛ معزول نطاقًا]
│        │    └── بوابة عميل A [دعوة، رؤية وتصرفات محددة]
│        └── العميل ClientWorkspace B
│             └── بوابة عميل B [دون اطلاع على A]
│
└── مساحة مستأجر عبر نطاقه المخصص أو بوابته
     └── طلب خدمة خاص بهذا المستأجر ──> طلبات المستأجر نفسه

وحدة المؤثرين: مجال وظيفي مخوّل Tenant/Client Scope
    ├── سجل المؤثرين
    ├── ترشيحات وموافقات
    ├── تعاونات ومخرجات
    └── الوصول المحدود للمؤثر المدعو إلى عروضه ومخرجاته وحدها
```

**تعاريف صارمة:**
- **Platform**: مالك SaaS، يراقب التسجيلات والاشتراكات، والتحصيل، وطلبات خدماته هو، والمساحات والسياسات والتشغيل. لا يقرأ تلقائيًا محتوى حملات العملاء؛ أي دعم تشخيصي استثنائي يتطلب تفويضًا وصلاحية وتدقيقًا.
- **Tenant/Workspace**: مساحة مشترك مستقلة ذات مالك وعضويات وباقة وفوترة وتكاملات وموارد وبيانات.
- **Solo/Team/Agency**: باقات أو قدرات ومسارات تشغيل، لا مبرر لإنشاء قاعدة بيانات أو محرك تقارير مختلف لكل فئة.
- **ClientWorkspace**: عميل الوكالة، يمكن أن يضم **عدة Projects**؛ العميل محور الواجهة، لكن المشروع كيان حقيقي يحتفظ بهويته ومصادره ومقاييسه.
- **Project**: حد انتقاء الموارد وربط حسابات الإعلان والمتاجر وGA4 والتقارير؛ لا يجوز تسطيحه أو نقله لمشروع آخر تلقائيًا.
- **Client Portal**: دعوة لهوية متحققة، مع صلاحيات تخص عميلًا محددًا؛ قد يرتبط المستخدم بأكثر من بوابة عميل، لكن كل سياق يعرض واحدًا فقط.
- **Influencer**: سجل/متعاون ليس مالك مساحة SaaS بحكم كونه مؤثرًا. قيمة الأجر وتكاليف الوكالة ومحتواها الداخلي لا تُكشف للمؤثر أو للعميل إلا بصلاحية ومادة عرض مصرح بها.

## 2. فصل التجارة عن التشغيل: أنواع السجلات

| النوع | ما يمثله | مالك السجل | موقع الإدارة | نهاية الرحلة |
|---|---|---|---|---|
| `platform_registration` | طلب الاشتراك في Solo/Team/Agency | Platform | Super Admin → التسجيلات | تحقق، مراجعة، دفع مثبت/إعفاء موثق، مساحة وعضوية |
| `platform_service_request` | شراء خدمة يقدمها مالك CampaignsHub من `#services` | Platform | Super Admin → الطلبات | تقييم، تعيين، عرض، تنفيذ، إغلاق |
| `tenant_service_request` | طلب لجهة مشتركة (وكالة/فرد) عبر نطاقها أو بوابتها العامة | Tenant محدد | المساحة → الطلبات | معالجة لدى ذلك المستأجر |
| `client_portal_request` | طلب عميل حالي داخل بوابته | Tenant + ClientWorkspace | مساحة الوكالة → الطلبات، وسياق العميل | رد، اعتماد، متابعة |
| `lead_form_submission` | مهتم من نموذج حملة أو منصة إعلانية | Tenant + Project | المهتمين | متابعة/تأهيل وتحويل فرص |
| `influencer_service_request` | طلب عمومي لخدمة مؤثرين يقدمها مالك المنصة | Platform | Super Admin → الطلبات (نوع: مؤثرين) | استيفاء/تسعير/تعاقد؛ لا ينشئ تعاونًا في Tenant عشوائي |
| `influencer_nomination/collaboration` | ترشيح/اتفاق/تسليم لدى مساحة مشتركة | Tenant (+ ClientWorkspace للتعاون) | مجال المؤثرين | موافقة/اتفاق/تسليم/قياس |

**ممنوع** اعتبار كل ما يحمل الاسم `request` كيانًا متطابقًا. يمكن توفير شاشة موحدة **للعرض والفرز** على مستوى مالك المنصة عبر إسقاطات/Adapters واضحة، **مع بقاء ملكية السجلات والقواعد والحدود منفصلة**.

### سؤال «إلى أين يذهب؟» — مخطط قرار ملزم

```text
وصل طلب جديد
│
├── اشتراك SaaS من موقع CampaignsHub؟ -> Platform Registration فقط
├── خدمة معروضة بصفحة خدمات CampaignsHub الرسمية؟ -> Platform Service Inbox فقط
├── طلب عبر نطاق/بوابة مستأجر موثوق ومحدد؟ -> Tenant Request لذلك المستأجر فقط
├── داخل جلسة بوابة عميل متحقق؟ -> ClientWorkspace + Tenant من الجلسة
├── نموذج مهتمين يتبع حملة؟ -> Project + Tenant المُعرَّف من النموذج
└── لا يمكن إثبات المالك/النطاق؟ -> رفض آمن + سجل تشخيص، لا افتراض Tenant أول/افتراضي
```

**قانون الملكية:** مصدر/نطاق الموقع + سياق مصدّق + نوع الرحلة يحدّد المالك صراحةً من الخادم. لا تحدد `tenant_id` من payload غير موثوق، ولا يُكفي اختيار خدمة إعلانية لتحديد الوكالة المالكة.

## 4. الهيكل المرئي المستهدف

### 4.1 إدارة المنصة — Super Admin
- **الرئيسية**: تسجيلات جديدة، خدمات مطلوبة، دفعات معلّقة، تشغيل، تنبيهات.
- **التسجيلات**: طلبات الاشتراك، التحقق، المراجعة، الموافقات، حالات الدفع والتفعيل.
- **الطلبات**: خدمات CampaignsHub الواردة من الموقع؛ النوع، العميل المحتمل، المسؤول، SLA، العرض، الحالة.
- **المساحات**: أصحاب المساحات، نوع الاشتراك، العزل، الوصول، صحة الربط، القيود.
- **المشتركين**: حسابات العملاء الدافعين وعلاقاتهم بالباقات والاشتراكات (تجنب تكرار عرض «المساحات» دون فائدة).
- **الباقات**: الأسعار، المزايا، الحدود، التجديد، التجربة، الخصومات والإضافات.
- **الخدمات**: كتالوج خدمات CampaignsHub الظاهر للزوار؛ التفعيل والانتقال للاستمارة والتصنيف.
- **المدفوعات**: فوترة اشتراكات SaaS ورسوم خدمات مالك المنصة، بتسويات منفصلة.
- **الدعم**: تذاكر ودعم، وصول استثنائي مضبوط إلى مساحة العميل.
- **التشغيل**: صحة الربط والمزامنة والمهام والطوابير والأخطاء وسجلات التدقيق.
- **الإعدادات**: الحساب، هوية المنصة، رسائل البريد، بوابات الدفع، سياسات التسجيل والصلاحيات.

### 4.2 مساحة الوكالة Team/Agency
- **الرئيسية**
- **الحملات**: الحملات، المحتوى
- **النتائج**: التحليلات، التقارير، المهتمين
- **المالية**: الميزانيات، الفواتير
- **العمليات**: العملاء، الطلبات، التنبيهات، المهام، الأتمتة
- **الإعدادات**: التكاملات، الفريق، الصلاحيات، الاشتراك، الحساب

**داخل «العملاء»**: مشروع/مشاريع، مصادر مرتبطة، الأرصدة، الطلبات، المحادثات، بوابة العميل، الفريق، التقارير. **داخل «الطلبات»**: صندوق عمل المستأجر العابر للعملاء (الوارد من نطاقه/بواباته)، مع فلاتر عميل/نوع/مسؤول/حالة. لا تكرر قوائم مستقلة لذات السجل.

### 4.3 مساحة Solo
الرئيسية، الحملات، المحتوى، التحليلات، التقارير، المهتمين، الميزانيات، التنبيهات، الإعدادات. بقية المزايا وفق الباقة؛ الإخفاء في الواجهة **ليس** تصريحًا للوصول.

### 4.4 بوابة العميل الخارجي
الرئيسية/الأداء، الحملات، التقارير، الطلبات، المحادثات، الفواتير، الاعتمادات/المحتوى **إذا سمحت الوكالة**. سياق عميل واحد فقط، والأفعال المقيدة تتحقق على الخادم.

### 4.5 المؤثرون
التعاونات، المؤثرين، الترشيحات، المخرجات، الأثر في واجهة إدارة الخدمة المرخّصة؛ المؤثر المدعو لا يرى إلا عروضه/تسليماته، ولا يرى دفتر مالك المساحة أو هامش الربح.

> **التصميم ليس إثبات تنفيذ.** لا تنقل فعليًا مسارًا أو تكسر bookmark قبل جرد سلوك التنقل والروابط القديمة.

## 5. متطلبات الأمان غير القابلة للتنازل

### P0 — فصل المالك وحدود البيانات
1. **Platform/Tenant separation:** مالك المنصة لا يُنشأ له Tenant تلقائي للتشغيل الإداري؛ استعلامات Super Admin cross-tenant تكون لغرض إداري محدد ومسموح، مع سجلات تدقيق، دون منح وصول افتراضي لحملات العملاء.
2. **Tenant isolation:** كل GET/POST/PATCH/DELETE وExport وReport وJob وWebhook وNotification وSearch وCache وFile/Media يتحقق من `tenant_id` المشتق من سياق موثوق.
3. **Client/Project scope:** داخل الوكالة يجب احترام ClientWorkspace + Project + resource binding؛ لا تسرّب عدادات أو أسماء أو نتائج خارج صلاحية العضو، حتى في «كل العملاء».
4. **No frontend-only authorization:** إخفاء القوائم لا يكفي. التحقق من Backend policies وmembership مع كل عملية.
5. **Public intake authenticity:** الفصل بين دومين مالك المنصة ودومينات المشتركين يتم في جهة الخادم وبمبدأ deny-by-default؛ لا يعتمد على `Referer` ولا `Origin` وحده ولا `tenant_id` مرسل من الزائر.
6. **No cross-routing:** طلب SaaS أو خدمة من CampaignsHub لا يظهر في وكالة مشتركة، وطلبات وكالة لا تظهر في Super Admin «خدمات المنصة» باعتبارها طلبات مالك المنصة.
7. **Object access:** توكن التتبع عام بصلاحية محصورة بطلب واحد، مع hashing وTTL/rate limit حسب التصميم الفعلي؛ لا يتحول إلى جلسة عميل ولا يكشف ملاحظات داخلية أو بيانات مستأجر آخر.
8. **Duplicate/idempotency:** تكرار submit أو webhook أو retry لا ينشئ مساحة أو اشتراكًا أو دفعة أو عميلًا أو تعاونًا مرتين.
9. **Payments:** لا تفعيل عضوية أو مساحة باشتراك مدفوع إلا وفق حالة الدفع المؤكدة عبر بوابة الدفع، مع السماح فقط بإعفاء/تجربة مصرّح بهما ومؤرشفين. فصل تسوية خدمة مالك المنصة عن الاشتراك عن فاتورة وكالة لعميلها.
10. **Invitations:** قبول الدعوة من المستخدم المقصود بهوية متحققة، مع انتهاء/إبطال وعدم إعادة استخدام، وعدم وراثة صلاحيات مساحة أخرى.
11. **Influencer confidentiality:** سجل المؤثر العام للمستأجر ليس إذنًا لرؤية تعاونات عملاء الآخرين؛ تكلفة المؤثر وهامش الوكالة معلومات خاصة.
12. **Audit:** تسجيل من أنشأ/وافق/رفض/نقل/حوّل الطلب؛ tenant/client/project/actor/type/timestamp، دون أسرار أو روابط توكن صريحة.
13. **External credentials:** المفاتيح والتجارب الحية وحالات المزوّد تصنَّف `BLOCKED_EXTERNAL_CREDENTIALS` لا Demo أو VERIFIED؛ لا تنفذ استدعاءات mutating لمزوّد دون تفويض.
14. **Safe migrations:** أي تغيير schema إضافي، قابل للتراجع، مع بيانات قديمة، backfill تجريبي أولًا؛ لا تعيد تعيين `tenant_id` لطلبات سابقة بالاستنتاج.
15. **Tenant deletion/suspension:** تعليق مساحة لا يحذف بياناتها ولا ينقل ملكية طلباتها. سياسة الاحتفاظ والحذف وفق المتطلبات القانونية والتعاقدية، لا تلقائيًا بناءً على قائمة جديدة.

## 6. منطق العمل: حالات وملكية وتحويلات

### 6.1 تسجيل SaaS
`draft → verification_required → pending_approval → approved_awaiting_payment → payment_pending → active`
مع الحالات الجانبية `rejected/cancelled/expired/suspended/past_due` حسب المحرك الحالي، **دون فرض انتقال خطي واحد إن كانت سياسة الإدارة تسمح بإعفاء موثق أو Trial**.

حقول ضرورية: `registration_id`, `owner_account`, `plan`, `billing_interval`, `verification_policy`, `review_decision`, `payment_reference`, `provisioned_tenant_id`، مع uniqueness/idempotency وaudit.

### 6.2 خدمة مالك المنصة
`new → qualified → assigned → quoted → accepted → in_progress → completed`، مع حالات جانبية `needs_information / rejected / cancelled` **كتصميم مستهدف؛ لا تفترض وجود هذه الأسماء في DB**.

حقول لازمة: `source=campaignshub_site`, `owner_scope=platform`, `service_key`, `public_reference`, `contact`, `assigned_admin`, `sla`, `quote`, `related_registration_id?`, `related_tenant_id?`, `conversion_id?`.

**مهم:** شراء خدمة إدارة حملات من مالك SaaS **لا يُنشئ تلقائيًا اشتراك SaaS أو وكالة مالكة**. إذا تقرر تقديم الخدمة من مساحة تشغيل مملوكة للشركة، فهذه خطوة تحويل صريحة ومنفصلة وآمنة، تُوثق علاقتها بالطلب الأصلي ولا تمنح حق الوصول للمستأجرين الآخرين.

### 6.3 طلب وكالة أو بوابة عميل
`new → assigned → in_progress → awaiting_client → completed` مع إغلاق/إلغاء. مستأجر واحد، وقد يكون عميل واحد؛ صلاحيات المدير تختلف عن طالب الخدمة.

### 6.4 المؤثرين
طلب خدمة عامة (مالك المنصة) ≠ مرشح مؤثر ≠ تعاون ≠ تسليم ≠ قياس أثر. الربط يتم بأحداث تحويل موثقة، وليس بنقل صف الطلب إلى جدول آخر أو نسخ بلا صلة مرجعية.

### 6.5 المهتمين
نموذج مهتم في حملة يظل `lead_form_submission` مسندًا للمشروع/العميل؛ يمكن أن يؤدي إلى فرصة أو طلب خدمة **بإجراء واضح** دون مسح أصل المصدر/UTM أو احتساب تحويل مرتين.

## 8. ترتيب المراجعة والتنفيذ دون كسر النظام

**الدفعة A — إثبات الوجهات (قراءة فقط):**

# CampaignsHub — الميزانيات والمالية والتجديد والتحويل إلى الريال
**مواصفة تنفيذ تراكمية — 13 نوفمبر 2026**

## 1. المبدأ الحاكم
المطلوب شاشة واحدة تعطي صاحب الوكالة ومدير المشروع والمالية الإجابة عن: **كم الميزانية المعتمدة؟ كم الإنفاق الفعلي؟ كم المتبقي؟ متى ينفد؟ ومن يحتاج تجديدًا؟**، مع زر **«زيادة الميزانية»** يضيف دفعة على رصيد العميل الحالي، بلا تصفير للإنفاق أو إعادة إنشاء ميزانية قديمة.

هذا العمل يخص **تمويل الإعلانات داخل مساحة الوكالة**، لا رسوم اشتراك CampaignsHub SaaS ولا الفواتير وحدها. يُطبّق مع `CampaignsHub_MASTER_FINAL_COMPLETE_2026-11-11.md` والعقد الهيكلي والأمني ومصفوفة المتطلبات؛ Git هو مرجع حالة التنفيذ. لا تعِد تنفيذ VERIFIED.

## 2. الوضع الحالي الذي يجب إعادة استخدامه
- `ClientBudgetController` / `ClientBudgetRollup`: جمع ميزانيات **الحملات** حسب العميل والمشروع؛ لا يثبت الأموال التي حوّلها العميل.
- `SpendLimitGovernor` / `SpendLimitsPage`: حدود إنفاق للمتابعة ضمن فترات؛ **ليست أرصدة تمويل، ولا تؤكد إيقاف منصة الإعلان**.
- `FinanceCenterController` / `FinanceOverviewPage`: عروض وفواتير ومدفوعات. فاتورة مدفوعة ليست تلقائيًا ميزانية حملة.
- `OfficialPegs` و`CurrencyRateFeed`: تحويل مؤرخ وموثق؛ USD→SAR = 3.75 وفق الربط الرسمي، والعملات العائمة تحتاج أسعارًا مؤرخة موثوقة. لا تعتمد سعر اليوم للإنفاق القديم، ولا تخمن عملة حساب.
- وجود الأجزاء السابقة لا يعني اكتمال **دفتر رصيد العميل** في الإنتاج. افحص الكود والـAPI والبيانات قبل إنشاء أي جداول جديدة.

## 3. الكيانات والمبالغ — تفريق إلزامي
| الاسم على الواجهة | المعنى | أين يؤثر؟ |
|---|---|---|
| **الميزانية** | مجموع أرصدة التمويل المعتمدة من العميل، بما فيها التجديدات | يزيد رصيد العميل |
| **الإنفاق** | مصروف حقيقي يومي من الحسابات الإعلانية المرتبطة | يخصم إذا التمويل «مسبق» ويشمل الحساب |
| **المتبقي** | التمويل المعتمد − الإنفاق المحتسب ± التسويات | مقياس قرار التجديد |
| **الخطة** | المبلغ أو فترة الإنفاق المستهدفة للحملات | مؤشر تخطيطي مستقل، ليس رصيدًا مقبوضًا |
| **حد الإنفاق** | حد مراقبة/قاعدة أتمتة حسب النطاق والفترة | لا يساوي التمويل ولا يوقف الإعلانات تلقائيًا |
| **الفواتير** | قيمة مطالبة مالية وحالة تحصيل | تُربط بالتمويل عند الإثبات فقط؛ دون خصم أو إضافة مكررة |

**الصيغة:** `المتبقي = الرصيد الافتتاحي + مجموع إضافات الميزانية المعتمدة − الإنفاق الفعلي القابل للخصم ± التسويات المعتمدة`.
أنماط التمويل: **مسبق / مباشر / لاحق**. حساب يُدفع مباشرة للمنصة أو خارج ميزانية العميل يعرض إنفاقه في مستقل، ولا يخفض رصيد التمويل المسبق.

## 4. تجديد العميل — زر «زيادة الميزانية»
**المكان:** `المالية ← الميزانيات`، وكل بطاقة عميل، و`العميل ← الرصيد` بصلاحية مناسبة.

**المسار:**
1. اختر العميل، وحدد المشروع عند الحاجة؛ افتراضيًا تمويل العميل يشمل مشاريعه وفق سياسة توزيع ظاهرة، وليس افتراضًا مخفيًا.
2. تظهر قبل الإدخال: **الميزانية الحالية، الإنفاق حتى آخر مزامنة، المتبقي الحالي، تاريخ آخر تحديث**.
3. اختر «زيادة الميزانية»، أدخل مبلغًا موجبًا بالريال، وتاريخ التحويل، ومرجع العملية، وملاحظة، وإثباتًا اختياريًا في تخزين خاص. أزرار سريعة 5,000/10,000/20,000/50,000 مع قيمة مخصصة.
4. سجل الإضافة `بانتظار الاعتماد` عند الحاجة؛ لا يزداد التمويل إلا بعد اعتماد مخوّل أو تحقق سياسة التحصيل، مع الفصل بين مُنشئ التسوية ومُعتمدها حيث يلزم.
5. عند الاعتماد، أنشئ حركة **إضافة** واحدة جديدة. لا تستبدل الأصل، ولا تصفّر الإنفاق، ولا تغيّر حدًا في المنصة الإعلانية بصمت.
6. بعد الحفظ: إشعار «زادت ميزانية [العميل] بمبلغ ... ر.س»، وتحديث الأرقام والخط والحلقة والتنبيهات فورًا، وزر «راجع توزيع الميزانية» إذا كانت الحملات تحتاج تعديل خطة مستقل.
7. **السجل:** تاريخ كل إضافة، المبلغ، المرجع، من أدخلها، من اعتمدها، الإثبات، الحالات، الرصيد قبل/بعد. خطأ في إضافة معتمدة يعالج بحركة عكسية موثقة لا بحذف الصف.
8. تكرار الضغط أو إعادة إرسال الطلب/الإشعار لا يضيف الميزانية مرتين. استخدم مفتاح idempotency، وقيدًا فريدًا منطقيًا، ومعاملة DB واختبار التزامن.

**مثال قبول ملزم (بيانات تجريبية):**
- الميزانيات السابقة: `10,000 + 7,500 + 3,750 + 20,000 = 41,250 ر.س`.
- الإنفاق: `30,711 ر.س` → المتبقي **10,539 ر.س**.
- اعتماد زيادة `20,000 ر.س` → الميزانية الجديدة **61,250**، الإنفاق **30,711**، المتبقي **30,539**.
- إنفاق جديد `1,000 ر.س` → المتبقي **29,539**. إعادة مزامنة الحساب لنفس اليوم **لا تغيره**.

## 5. التحويل إلى الريال السعودي
- **جميع إجماليات الميزانية والإنفاق والمتبقي والتوزيع والتنبيهات والبريد** تعرض بوحدة ر.س داخل شاشة ميزانيات الوكالة، مع زر تفاصيل يعرض قيمة و**عملة الحساب الأصلية**.
- **ميزانيات الحملات الأجنبية** تتحول إلى الريال لأغراض العرض والمقارنة، ولا تغيَّر ميزانية الإعلان الحقيقية عند Meta/Google/TikTok/X/LinkedIn/Snapchat.
- تحويل **الإنفاق يتم يومًا بيوم** بسعر يوم الإنفاق الموثق. احفظ القيمة الأصلية/العملة/سعر الصرف/تاريخه/مصدره؛ الأسعار التاريخية لا تُستبدل بسعر اليوم عند فتح التقرير.
- USD 100 = **375 ر.س** عند معدل USD→SAR 3.75 الموثق. للعملات غير المربوطة يلزم مصدر سعر مؤرخ؛ إذا تعذر: **«غير محوّل»** مع عدد السجلات والمبلغ الأصلي، ولا تعرض الإجمالي الجزئي بوصفه كاملًا أو المتبقي بوصفه مؤكدًا.
- لكل حساب إعلاني وتاريخ ومصدر ومشروع محدد صف فعلي فريد أو آلية مكافئة. إعادة المزامنة **تحدث الفارق ولا تضيف الخصم مرتين**؛ وتحتفظ بتدقيق التعديل.
- افحص الحسابات المشتركة بين المشاريع، والأيام السابقة لأول ميزانية، والتواريخ الافتتاحية حتى لا يحدث خصم مزدوج. استيراد رصيد افتتاحي بتاريخ قطع لا يجمع أيضًا التمويل والإنفاق القديمين المضمنين فيه.
- حالة نقص البيانات أو فشل المزامنة تعرض «الإنفاق غير مكتمل» و«المتبقي غير مؤكد» مع آخر وقت معروف، لا صفرًا ولا اطمئنانًا خاطئًا.

## 6. تصميم الشاشة — معلومات أكثر، تمرير أقل
**1366×768:** لا تستهلك الشاشة بمقدمات كبيرة؛ القرار يظهر من أول نظرة.

```text
┌ الميزانيات ─────── كل العملاء ▾  الفترة ▾  المنصات ▾  آخر تحديث  [زيادة الميزانية] ┐
│  الميزانية  |  الإنفاق  |  المتبقي  |  الأقرب للتجديد                       │
├───────────────────────────────────────┬────────────────────────────────────────┤
│ خط المتبقي عبر الأيام                 │ حلقة المتبقي + سرعة الصرف + أيام متوقعة │
│ النزول = إنفاق / الارتفاع = تجديد     │ نسبة الإنفاق من الميزانية المعتمدة      │
├───────────────────────────────────────┴────────────────────────────────────────┤
│ توزيع الإنفاق: Meta ▰ Google ▰ Snap ▰ TikTok ▰ X ▰ LinkedIn                  │
├───────────────────────────────────────────────────────────────────────────────┤
│ العميل  | الميزانية | الإنفاق | المتبقي | % المتبقي | أيام | الحالة | [+ زيادة]  │
│ الأقرب للنفاد أولًا  · بحث وتصفية · تفاصيل عند الضغط                         │
└───────────────────────────────────────────────────────────────────────────────┘
```

- **صف بطاقات الأرقام:** الميزانية، الإنفاق، المتبقي، «يحتاج تجديد» مع مقارنة الفترة ومصدر الرقم. كل رقم بـر.س؛ استثناء «غير محوّل» ظاهر بجواره.
- **الخط الأساسي:** **المتبقي يوميًا**، مع أعمدة اختيارية للإنفاق اليومي، و**قفزة واضحة + وسم مبلغ التجديد وتاريخه** عندما يضيف العميل ميزانية.
- **الرسم الحلقي:** نسبة الإنفاق من مجموع التمويل، والمتبقي في الوسط؛ الرصيد السالب يظهر «تجاوز الميزانية» بدل دائرة مضللة.
- **شريط المنصات:** توزيع الإنفاق الحقيقي لكل منصة؛ لون ثابت، تفاعل باللمس/المرور، مع تفاصيل المبلغ الأصلي وصرفه.
- **جدول العملاء المكثف:** اسم العميل، ميزانيته، إنفاقه، المتبقي ونسبته، أيام التغطية، الحالة، «زيادة». ترتيب تحذيري، بحث، فلاتر، والنقر يفتح Drawer جانبي بدل صفحة مزدحمة.
- **تفاصيل العميل:** رسوم حسب المشروع والحساب والحملة؛ كل زيادات التمويل، التسويات، الإنفاق اليومي، أرصدة افتتاحية، الإيصالات، كشف حساب PDF، وسجل التغيرات.
- **الجوال 320–430px:** أرقام 2×2، رسم كامل العرض، بطاقات للعملاء بدل جدول أفقي، زر زيادة واضح، التفاصيل في صفحة أو Accordion. لا تمرير **أفقي للصفحة** ولا عناصر خارج الشاشة أو أزرار تغطيها لوحة المفاتيح.
- **ملاحظة واقعية:** 30 عميلًا مع جميع التفاصيل يستحيل عرضهم كاملين دون تمرير رأسي على 768px؛ أظهر ملخص القرار وأول العملاء المستعجلين فوق الطيّة، والبقية عبر قائمة قصيرة/بحث/تفاصيل. لا تخفِ وظيفة أو رقمًا فقط لتحقيق «صفر تمرير».

## 7. التنبيهات والتمويل المتجدد
- تنبيهات عند استهلاك **75%، 90%، 100%** من الميزانية المعتمدة، وعند **المتبقي ≤ 0**، أو نفاد متوقع خلال **7 أيام** بشرط بيانات كافية.
- المستلمون: المالية ومدير المشروع المصرح له بذلك العميل، وبريد خارج النظام **بموافقة صريحة ونطاق محدود**؛ دون كشف بقية العملاء.
- نص موحد بسيط: **«عميل [اسم] — المتبقي 1,250 ر.س. يكفي نحو 3 أيام حسب الإنفاق الحالي. جدّد مع العميل أو راجع خطة الصرف.»** مع رابط للرصيد الصحيح.
- إذا نقص سعر صرف: **«جزء من الإنفاق غير محوّل للريال؛ راجع أسعار الصرف»**، مع تعليق التنبؤ لا تعويضه برقم مختلق.
- **بعد زيادة الميزانية:** أعد حساب المتبقي والحدود والأيام؛ أغلق/حدث التنبيهات القديمة بتدقيق دون حذف تاريخها، ولا ترسل نفس مستوى التنبيه في كل مزامنة. يمكن إنشاء جيل تمويل جديد `funding_cycle` لمنع تكرار 75/90/100 إلا بعد عبور جديد للحدود.
- الربط بمحرك التنبيهات والبريد القائم، لا محرك مستقل؛ حد المتابعة لا يوقف الإعلانات إلا بقاعدة أتمتة **منفّذة ومفعّلة**.

## 8. الأمان والأدوار
كل إضافة واعتماد وقراءة ورابط ملف أو كشف تحترم Tenant وClientWorkspace وProject والقدرات الفعلية. مدير المشروع يرى عملاءه فقط، والمالية ترى ما يسمح به دورها، والعميل يرى رصيده فقط إذا فُتح له. أي كشف PDF أو إيصال لا يكشف مساحة أو عميلًا آخر. الدفتر يستخدم Decimal/أعدادًا صحيحة دقيقة وليس float للحركات المحاسبية، ويعالج ازدواج webhooks ومحاولات الإرسال والـretry.

## 10. دفعات تنفيذ مغلقة
- **F0: جرد دقيق مختصر** — تحقق من حدود الموجود في Git ومصفوفة المتطلبات؛ لا تختبر أو تصلح VERIFIED مجددًا.
- **F1: دفتر التمويل + زيادة الميزانية** — العمليات والإضافات المعتمدة والتدقيق وidempotency. هذه أول دفعة إذا لم تثبت ثغرة P0 أعلى منها.
- **F2: خصم الإنفاق + SAR** — daily facts ومنع التكرار وأسعار تاريخية وحالة النقص.
- **F3: التنبيهات** — 75/90/100 والتوقع وإعادة الضبط بعد التجديد وبريد المعنيين.
- **F4: الشاشة والرسوم والجوال** — الصفحة الأولى، خط الرصيد مع قفزات التمويل، قائمة كثيفة وDrawer، 320–1440، RTL/LTR.
- **F5: كشف الحساب والتسويات والبوابة والتقارير** — الربط بالصلاحيات القائمة، ثم التحقق الحي.

لكل دفعة صغيرة: PR واحد واختبارات موجهة وCI وLander وDeploy والتحقق المصرح به، وتحديث المصفوفة وتقرير حالة، ثم توقف. افتح أي مشكلة صلاحية/مالك بيانات P0 مثبتة قبل البدء في الماليات.
