# CampaignsHub — العقد الهيكلي والأمني ومسارات الطلبات
**Structural Architecture, Ownership & Security Verification Contract**  
الإصدار: 1.0 — 11 نوفمبر 2026  
النوع: مرجع هيكلي تراكمي للتدقيق والتنفيذ الآمن، **ليس إثباتًا أن جميع البنود منفذة إنتاجيًا**.

## 0. الهدف ومصادر الحقيقة

**CampaignsHub منصة SaaS متعددة المستأجرين** لإدارة الحملات الإعلانية المدفوعة، والتكاملات والمتاجر، والتحليلات، والتقارير التفاعلية القابلة للمشاركة، مع خدمات أخرى يقدمها مالك المنصة. **مالك المنصة (Super Admin) ليس وكالة مشتركة؛ ولا يجوز معاملة مساحته أو طلبات خدماته العامة كبيانات أي مستأجر.**

ترتيب الحقيقة عند التعارض:
1. Git الحالي (`origin/main`)، الـPRs وCI وDeploy وسلوك Production الموثق.
2. `docs/REQUIREMENTS_TRACEABILITY_MATRIX.md` وسجل العيوب و`docs/RESUME_STATE.md`.
3. المتطلبات الدائمة وملفات تسليم المشروع وملف التنفيذ التراكمي وملف منصة التكاملات الموحدة.
4. هذا الملف مرجع لتصحيح **الهيكل والملكية والحدود**؛ لا يمحو ما قبله ولا يعيد تنفيذ VERIFIED.

**حالات التنفيذ الإلزامية:** `NOT_STARTED`، `IN_PROGRESS`، `PARTIAL`، `IMPLEMENTED_NOT_VERIFIED`، `VERIFIED`، `BLOCKED_EXTERNAL_CREDENTIALS`، `BLOCKED_OPERATIONAL_EVIDENCE`. لا يصح استبدالها بعبارة عامة «مكتمل».

## 1. الطبقات والكيانات: لا تخلط صلاحياتها

```text
CampaignsHub.io (الموقع العام / التسويق / الأسعار / الخدمات)
│
├── طلب اشتراك SaaS ──> نطاق إدارة المنصة (Platform Registration)
│                            └── مراجعة / تحقق / قرار / دفع مثبت / إنشاء مساحة
│
├── طلب خدمة مقدمة من CampaignsHub ──> صندوق خدمات مالك المنصة
│                                         └── مسؤول / عرض / تعاقد / تنفيذ / إغلاق
│
├── وصول المستخدمين الحاليين
│   ├── إدارة المنصة Super Admin [عبر بوابة منصة مستقلة؛ بلا tenant membership]
│   ├── مساحة Solo / مستقل / معلن [Tenant]
│   └── مساحة Team / Agency [Tenant]
│        ├── العميل ClientWorkspace A
│        │    ├── مشروع 1 [ربط الموارد والحملات والبيانات]
│        │    ├── مشروع 2 [اختياري؛ معزول نطاقًا]
│        │    └── بوابة عميل A [دعوة، رؤية وتصرفات محددة]
│        └── العميل ClientWorkspace B
│             └── بوابة عميل B [دون اطلاع على A]
│
└── مساحة مستأجر عبر نطاقه المخصص أو بوابته
     └── طلب خدمة خاص بهذا المستأجر ──> طلبات المستأجر نفسه

وحدة المؤثرين: مجال وظيفي مخوّل Tenant/Client Scope
    ├── سجل المؤثرين
    ├── ترشيحات وموافقات
    ├── تعاونات ومخرجات
    └── الوصول المحدود للمؤثر المدعو إلى عروضه ومخرجاته وحدها
```

**تعاريف صارمة:**
- **Platform**: مالك SaaS، يراقب التسجيلات والاشتراكات، والتحصيل، وطلبات خدماته هو، والمساحات والسياسات والتشغيل. لا يقرأ تلقائيًا محتوى حملات العملاء؛ أي دعم تشخيصي استثنائي يتطلب تفويضًا وصلاحية وتدقيقًا.
- **Tenant/Workspace**: مساحة مشترك مستقلة ذات مالك وعضويات وباقة وفوترة وتكاملات وموارد وبيانات.
- **Solo/Team/Agency**: باقات أو قدرات ومسارات تشغيل، لا مبرر لإنشاء قاعدة بيانات أو محرك تقارير مختلف لكل فئة.
- **ClientWorkspace**: عميل الوكالة، يمكن أن يضم **عدة Projects**؛ العميل محور الواجهة، لكن المشروع كيان حقيقي يحتفظ بهويته ومصادره ومقاييسه.
- **Project**: حد انتقاء الموارد وربط حسابات الإعلان والمتاجر وGA4 والتقارير؛ لا يجوز تسطيحه أو نقله لمشروع آخر تلقائيًا.
- **Client Portal**: دعوة لهوية متحققة، مع صلاحيات تخص عميلًا محددًا؛ قد يرتبط المستخدم بأكثر من بوابة عميل، لكن كل سياق يعرض واحدًا فقط.
- **Influencer**: سجل/متعاون ليس مالك مساحة SaaS بحكم كونه مؤثرًا. قيمة الأجر وتكاليف الوكالة ومحتواها الداخلي لا تُكشف للمؤثر أو للعميل إلا بصلاحية ومادة عرض مصرح بها.

## 2. فصل التجارة عن التشغيل: أنواع السجلات

| النوع | ما يمثله | مالك السجل | موقع الإدارة | نهاية الرحلة |
|---|---|---|---|---|
| `platform_registration` | طلب الاشتراك في Solo/Team/Agency | Platform | Super Admin → التسجيلات | تحقق، مراجعة، دفع مثبت/إعفاء موثق، مساحة وعضوية |
| `platform_service_request` | شراء خدمة يقدمها مالك CampaignsHub من `#services` | Platform | Super Admin → الطلبات | تقييم، تعيين، عرض، تنفيذ، إغلاق |
| `tenant_service_request` | طلب لجهة مشتركة (وكالة/فرد) عبر نطاقها أو بوابتها العامة | Tenant محدد | المساحة → الطلبات | معالجة لدى ذلك المستأجر |
| `client_portal_request` | طلب عميل حالي داخل بوابته | Tenant + ClientWorkspace | مساحة الوكالة → الطلبات، وسياق العميل | رد، اعتماد، متابعة |
| `lead_form_submission` | مهتم من نموذج حملة أو منصة إعلانية | Tenant + Project | المهتمين | متابعة/تأهيل وتحويل فرص |
| `influencer_service_request` | طلب عمومي لخدمة مؤثرين يقدمها مالك المنصة | Platform | Super Admin → الطلبات (نوع: مؤثرين) | استيفاء/تسعير/تعاقد؛ لا ينشئ تعاونًا في Tenant عشوائي |
| `influencer_nomination/collaboration` | ترشيح/اتفاق/تسليم لدى مساحة مشتركة | Tenant (+ ClientWorkspace للتعاون) | مجال المؤثرين | موافقة/اتفاق/تسليم/قياس |

**ممنوع** اعتبار كل ما يحمل الاسم `request` كيانًا متطابقًا. يمكن توفير شاشة موحدة **للعرض والفرز** على مستوى مالك المنصة عبر إسقاطات/Adapters واضحة، **مع بقاء ملكية السجلات والقواعد والحدود منفصلة**.

### سؤال «إلى أين يذهب؟» — مخطط قرار ملزم

```text
وصل طلب جديد
│
├── اشتراك SaaS من موقع CampaignsHub؟ -> Platform Registration فقط
├── خدمة معروضة بصفحة خدمات CampaignsHub الرسمية؟ -> Platform Service Inbox فقط
├── طلب عبر نطاق/بوابة مستأجر موثوق ومحدد؟ -> Tenant Request لذلك المستأجر فقط
├── داخل جلسة بوابة عميل متحقق؟ -> ClientWorkspace + Tenant من الجلسة
├── نموذج مهتمين يتبع حملة؟ -> Project + Tenant المُعرَّف من النموذج
└── لا يمكن إثبات المالك/النطاق؟ -> رفض آمن + سجل تشخيص، لا افتراض Tenant أول/افتراضي
```

**قانون الملكية:** مصدر/نطاق الموقع + سياق مصدّق + نوع الرحلة يحدّد المالك صراحةً من الخادم. لا تحدد `tenant_id` من payload غير موثوق، ولا يُكفي اختيار خدمة إعلانية لتحديد الوكالة المالكة.

## 4. الهيكل المرئي المستهدف

### 4.1 إدارة المنصة — Super Admin
- **الرئيسية**: تسجيلات جديدة، خدمات مطلوبة، دفعات معلّقة، تشغيل، تنبيهات.
- **التسجيلات**: طلبات الاشتراك، التحقق، المراجعة، الموافقات، حالات الدفع والتفعيل.
- **الطلبات**: خدمات CampaignsHub الواردة من الموقع؛ النوع، العميل المحتمل، المسؤول، SLA، العرض، الحالة.
- **المساحات**: أصحاب المساحات، نوع الاشتراك، العزل، الوصول، صحة الربط، القيود.
- **المشتركين**: حسابات العملاء الدافعين وعلاقاتهم بالباقات والاشتراكات (تجنب تكرار عرض «المساحات» دون فائدة).
- **الباقات**: الأسعار، المزايا، الحدود، التجديد، التجربة، الخصومات والإضافات.
- **الخدمات**: كتالوج خدمات CampaignsHub الظاهر للزوار؛ التفعيل والانتقال للاستمارة والتصنيف.
- **المدفوعات**: فوترة اشتراكات SaaS ورسوم خدمات مالك المنصة، بتسويات منفصلة.
- **الدعم**: تذاكر ودعم، وصول استثنائي مضبوط إلى مساحة العميل.
- **التشغيل**: صحة الربط والمزامنة والمهام والطوابير والأخطاء وسجلات التدقيق.
- **الإعدادات**: الحساب، هوية المنصة، رسائل البريد، بوابات الدفع، سياسات التسجيل والصلاحيات.

### 4.2 مساحة الوكالة Team/Agency
- **الرئيسية**
- **الحملات**: الحملات، المحتوى
- **النتائج**: التحليلات، التقارير، المهتمين
- **المالية**: الميزانيات، الفواتير
- **العمليات**: العملاء، الطلبات، التنبيهات، المهام، الأتمتة
- **الإعدادات**: التكاملات، الفريق، الصلاحيات، الاشتراك، الحساب

**داخل «العملاء»**: مشروع/مشاريع، مصادر مرتبطة، الأرصدة، الطلبات، المحادثات، بوابة العميل، الفريق، التقارير. **داخل «الطلبات»**: صندوق عمل المستأجر العابر للعملاء (الوارد من نطاقه/بواباته)، مع فلاتر عميل/نوع/مسؤول/حالة. لا تكرر قوائم مستقلة لذات السجل.

### 4.3 مساحة Solo
الرئيسية، الحملات، المحتوى، التحليلات، التقارير، المهتمين، الميزانيات، التنبيهات، الإعدادات. بقية المزايا وفق الباقة؛ الإخفاء في الواجهة **ليس** تصريحًا للوصول.

### 4.4 بوابة العميل الخارجي
الرئيسية/الأداء، الحملات، التقارير، الطلبات، المحادثات، الفواتير، الاعتمادات/المحتوى **إذا سمحت الوكالة**. سياق عميل واحد فقط، والأفعال المقيدة تتحقق على الخادم.

### 4.5 المؤثرون
التعاونات، المؤثرين، الترشيحات، المخرجات، الأثر في واجهة إدارة الخدمة المرخّصة؛ المؤثر المدعو لا يرى إلا عروضه/تسليماته، ولا يرى دفتر مالك المساحة أو هامش الربح.

> **التصميم ليس إثبات تنفيذ.** لا تنقل فعليًا مسارًا أو تكسر bookmark قبل جرد سلوك التنقل والروابط القديمة.

## 5. متطلبات الأمان غير القابلة للتنازل

### P0 — فصل المالك وحدود البيانات
1. **Platform/Tenant separation:** مالك المنصة لا يُنشأ له Tenant تلقائي للتشغيل الإداري؛ استعلامات Super Admin cross-tenant تكون لغرض إداري محدد ومسموح، مع سجلات تدقيق، دون منح وصول افتراضي لحملات العملاء.
2. **Tenant isolation:** كل GET/POST/PATCH/DELETE وExport وReport وJob وWebhook وNotification وSearch وCache وFile/Media يتحقق من `tenant_id` المشتق من سياق موثوق.
3. **Client/Project scope:** داخل الوكالة يجب احترام ClientWorkspace + Project + resource binding؛ لا تسرّب عدادات أو أسماء أو نتائج خارج صلاحية العضو، حتى في «كل العملاء».
4. **No frontend-only authorization:** إخفاء القوائم لا يكفي. التحقق من Backend policies وmembership مع كل عملية.
5. **Public intake authenticity:** الفصل بين دومين مالك المنصة ودومينات المشتركين يتم في جهة الخادم وبمبدأ deny-by-default؛ لا يعتمد على `Referer` ولا `Origin` وحده ولا `tenant_id` مرسل من الزائر.
6. **No cross-routing:** طلب SaaS أو خدمة من CampaignsHub لا يظهر في وكالة مشتركة، وطلبات وكالة لا تظهر في Super Admin «خدمات المنصة» باعتبارها طلبات مالك المنصة.
7. **Object access:** توكن التتبع عام بصلاحية محصورة بطلب واحد، مع hashing وTTL/rate limit حسب التصميم الفعلي؛ لا يتحول إلى جلسة عميل ولا يكشف ملاحظات داخلية أو بيانات مستأجر آخر.
8. **Duplicate/idempotency:** تكرار submit أو webhook أو retry لا ينشئ مساحة أو اشتراكًا أو دفعة أو عميلًا أو تعاونًا مرتين.
9. **Payments:** لا تفعيل عضوية أو مساحة باشتراك مدفوع إلا وفق حالة الدفع المؤكدة عبر بوابة الدفع، مع السماح فقط بإعفاء/تجربة مصرّح بهما ومؤرشفين. فصل تسوية خدمة مالك المنصة عن الاشتراك عن فاتورة وكالة لعميلها.
10. **Invitations:** قبول الدعوة من المستخدم المقصود بهوية متحققة، مع انتهاء/إبطال وعدم إعادة استخدام، وعدم وراثة صلاحيات مساحة أخرى.
11. **Influencer confidentiality:** سجل المؤثر العام للمستأجر ليس إذنًا لرؤية تعاونات عملاء الآخرين؛ تكلفة المؤثر وهامش الوكالة معلومات خاصة.
12. **Audit:** تسجيل من أنشأ/وافق/رفض/نقل/حوّل الطلب؛ tenant/client/project/actor/type/timestamp، دون أسرار أو روابط توكن صريحة.
13. **External credentials:** المفاتيح والتجارب الحية وحالات المزوّد تصنَّف `BLOCKED_EXTERNAL_CREDENTIALS` لا Demo أو VERIFIED؛ لا تنفذ استدعاءات mutating لمزوّد دون تفويض.
14. **Safe migrations:** أي تغيير schema إضافي، قابل للتراجع، مع بيانات قديمة، backfill تجريبي أولًا؛ لا تعيد تعيين `tenant_id` لطلبات سابقة بالاستنتاج.
15. **Tenant deletion/suspension:** تعليق مساحة لا يحذف بياناتها ولا ينقل ملكية طلباتها. سياسة الاحتفاظ والحذف وفق المتطلبات القانونية والتعاقدية، لا تلقائيًا بناءً على قائمة جديدة.

## 6. منطق العمل: حالات وملكية وتحويلات

### 6.1 تسجيل SaaS
`draft → verification_required → pending_approval → approved_awaiting_payment → payment_pending → active`
مع الحالات الجانبية `rejected/cancelled/expired/suspended/past_due` حسب المحرك الحالي، **دون فرض انتقال خطي واحد إن كانت سياسة الإدارة تسمح بإعفاء موثق أو Trial**.

حقول ضرورية: `registration_id`, `owner_account`, `plan`, `billing_interval`, `verification_policy`, `review_decision`, `payment_reference`, `provisioned_tenant_id`، مع uniqueness/idempotency وaudit.

### 6.2 خدمة مالك المنصة
`new → qualified → assigned → quoted → accepted → in_progress → completed`، مع حالات جانبية `needs_information / rejected / cancelled` **كتصميم مستهدف؛ لا تفترض وجود هذه الأسماء في DB**.

حقول لازمة: `source=campaignshub_site`, `owner_scope=platform`, `service_key`, `public_reference`, `contact`, `assigned_admin`, `sla`, `quote`, `related_registration_id?`, `related_tenant_id?`, `conversion_id?`.

**مهم:** شراء خدمة إدارة حملات من مالك SaaS **لا يُنشئ تلقائيًا اشتراك SaaS أو وكالة مالكة**. إذا تقرر تقديم الخدمة من مساحة تشغيل مملوكة للشركة، فهذه خطوة تحويل صريحة ومنفصلة وآمنة، تُوثق علاقتها بالطلب الأصلي ولا تمنح حق الوصول للمستأجرين الآخرين.

### 6.3 طلب وكالة أو بوابة عميل
`new → assigned → in_progress → awaiting_client → completed` مع إغلاق/إلغاء. مستأجر واحد، وقد يكون عميل واحد؛ صلاحيات المدير تختلف عن طالب الخدمة.

### 6.4 المؤثرين
طلب خدمة عامة (مالك المنصة) ≠ مرشح مؤثر ≠ تعاون ≠ تسليم ≠ قياس أثر. الربط يتم بأحداث تحويل موثقة، وليس بنقل صف الطلب إلى جدول آخر أو نسخ بلا صلة مرجعية.

### 6.5 المهتمين
نموذج مهتم في حملة يظل `lead_form_submission` مسندًا للمشروع/العميل؛ يمكن أن يؤدي إلى فرصة أو طلب خدمة **بإجراء واضح** دون مسح أصل المصدر/UTM أو احتساب تحويل مرتين.

## 7. مصفوفة فحوص الأمان والقبول

| # | السيناريو | القبول الإلزامي |
|---|---|---|
| S01 | زائر ينقر «اطلب خدمة» من `campaignshub.io/#services` | يسجل الطلب في صندوق مالك المنصة، لا Tenant وكالة افتراضية |
| S02 | زائر يقدم تسجيل اشتراك SaaS | يظهر في «التسجيلات» فقط، لا في «طلبات وكالة» |
| S03 | مستأجر A يفتح public intake في نطاقه | يسجّل في Tenant A فقط |
| S04 | مستأجر B يطلب `/agency/requests/{id_A}` | 404 أو منع آمن بلا عنوان أو رقم تسلسلي مسرب |
| S05 | مالك منصة يستعرض اشتراك وكالة | يرى metadata إدارية، لا تقارير حملة بلا تفويض |
| S06 | عميل A وبوابة عميل B | لا تظهر أسماء/فواتير/ملفات/محادثات/أرقام أحدهما للآخر |
| S07 | مدير مشروع لديه عميلان | كل بحث/إجمالي/تصدير وإشعار يقتصر عليهما |
| S08 | مستخدم يملك حسابًا في وكالتين | تبديل صريح للعضوية، ولا مزج في الجلسة/الكاش |
| S09 | طلب بلا نطاق أو مالك معتمد | يرفض مغلقًا ويُسجل السبب؛ لا `Tenant::first()` |
| S10 | طلب عام يصل عبر دومين مستأجر مزور أو Host غير موثوق | لا إعادة توجيه لخدمات المالك أو لمستأجر آخر؛ فحص host وtrust proxy |
| S11 | تكرار الضغط على إرسال طلب | لا تكرار غير مقصود ولا رسائل مزدوجة |
| S12 | Webhook دفع مكرر/متأخر/مزور | لا تفعيل أو تحصيل مكرر، والتحقق backend-to-backend |
| S13 | قبول دعوة من بريد مختلف | رفض، ولا تعيين دور في Tenant آخر |
| S14 | ملف/تقرير/تصدير عبر ID لمستأجر آخر | رفض؛ لا تسرب رابط S3 أو ملف مخزن |
| S15 | مؤثر من عميل A يطلب اتفاق عميل B | رفض؛ لا كشف هامش أو أجور سرية |
| S16 | خدمة مؤثرين عامة تم قبولها | تظل Platform-owned إلى أن تُنشأ علاقة تنفيذ صريحة |
| S17 | طلب بوابة العميل يظهر للموظف | رابط صحيح للمساحة وطلب محدد، وإشعار بالجهة المسؤولة |
| S18 | تعطل البريد أو 2FA أو المزود | الحالة صادقة `awaiting/failed`؛ لا رسالة نجاح كاذبة |
| S19 | مسار قديم إلى الطلبات أو التقارير أو النماذج | يبقى قابلًا للوصول للمالك الصحيح دون فتح صلاحيات |
| S20 | إيقاف/تخفيض باقة | لا حذف بيانات أو روابط عميل أو إعادة إسناد طلبات |
| S21 | سجل طلب تاريخي tenant ملكيته ملتبسة | `BLOCKED_OPERATIONAL_EVIDENCE`، لا إصلاح صامت |
| S22 | إرسال طلب من موقع الخدمة ثم موافقة في الإدارة | إسناد مسؤول وإشعار وسجل حالة ومسار تحويل، بدون طلب يتيم |

**طبقات الاختبار:** unit لمسار القرار؛ feature HTTP بالعزل والرفض؛ integration DB + queue/cache/notifications؛ Playwright عربي/إنجليزي والهاتف؛ اختبار Production قراءة فقط أو حسابات معزولة مخوّلة. لا إنشاء عملاء حقيقيين ولا إرسال مراسلات حقيقية ولا تنفيذ مدفوعات دون موافقة.

## 8. ترتيب المراجعة والتنفيذ دون كسر النظام

**الدفعة A — إثبات الوجهات (قراءة فقط):**
- خريطة فعلية `public URL → frontend route → API → controller → model → owner_scope → inbox → notification → conversion`.
- جرد أنواع الطلبات والـtenant domains وإعدادات public services وأزرار `#services`.
- استخرج مواضع `PortalTenantResolver` و`ExternalRequest` المتقاطعة، وطلبات لا مالك لها، مع بيانات مُخفاة الحساسية.
- أخرج `[الحالة، دليل Git، اختبار، دليل Production أو العائق]` لكل نقطة.

**الدفعة B — تصحيح ملكية الطلبات P0 (إذا أثبتت A خللًا):**
- فصل مصادر خدمات CampaignsHub عن public intake للمستأجرين، من دون إلغاء الرحلات العاملة.
- حدود ملكية صريحة، اختبارات fail-first، سياقات فائتة ترفض مغلقًا.
- إصلاح الإشعارات والمسؤول والـinbox؛ لا تعديل طلبات تاريخية بأثر رجعي من غير إذن.

**الدفعة C — تسجيل SaaS والمدفوعات والدعوات:**
- المسار الوحيد للقرار، إثبات الدفع، idempotency، إنشاء Tenant/عضوية، وتحكم خاصية plan/role.
- اختبارات تكرار وموافقة/رفض وتفعيل وسجل تدقيق.

**الدفعة D — طلبات الوكالات والبوابات والمؤثرين:**
- صلاحيات client/project، انتقال الحالات، تذاكر العميل، تتبع التعاقد، وسياق المؤثر.
- منع التكرار والخلط مع المهتمين.

**الدفعة E — واجهات وملاحة وتبسيط المسميات:**
- بعد إثبات ownership، التنظيم المقترح أعلاه، مع تحويل المسارات القديمة وRBAC؛ لا حذف واجهات عاملة دفعة واحدة.
- مركز التكاملات Project-First محفوظ من صفحة العميل وداخل الإعدادات وفق ملفه الأصلي؛ لا يعاد إنشاؤه.

**الدفعة F — تحقق نهائي وإغلاق:**
- اختبارات S01–S22، CI، Merge عبر Lander، Deploy، smoke على Production، توثيق أدلة لكل حالة.
- `VERIFIED` فقط للمسارات المثبتة حيًا؛ باقي العوائق تُسمى صراحةً.

## 9. متطلبات التغطية التراكمية

المسار الهيكلي **لا يستبدل** المتطلبات الفنية والتشغيلية السابقة: منصة التكاملات الموحدة، عزل مصادر التقارير، العملات، بيانات GA4 وسلة وزد، محتويات الإعلانات، عمليات المزامنة وWebhooks، التنبيهات، البريد، المالية، القوالب، الفلاتر والـDuplicate، والخصوصية. اربط كل بند في المصفوفة الأصلية، ولا تنشئ مصفوفة منافسة. احفظ `Project/ClientWorkspace` IDs والروابط العامة `/r/...` و`/f/...` والتكاملات القائمة.

### معيار الانتهاء من *المراجعة* (وليس التطوير)
ملف واحد `docs/SAAS_STRUCTURE_AND_REQUEST_ROUTING_AUDIT.md` فيه:

2. المسار المالك الصريح وRACI «من يستلم/يوافق/ينفذ/يُبلغ».
3. مقارنة مطلوب/موجود/مفقود مع أدلة قابلة للفحص وتصنيف حالة.

5. خطة دفعات صغيرة وربطها بصفوف مصفوفة المتطلبات السابقة.
6. بلا تعديل إنتاجي أو رسائل/مدفوعات حقيقية خلال الجرد.
