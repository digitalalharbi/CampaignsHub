# CampaignsHub — التوجيه التنفيذي الإلزامي P0

**التاريخ:** 2026-11-03  
**النطاق:** تسجيل الدخول، Meta، تحليلات GA4 والمتاجر، مصادر الزيارات وUTM، قياس أثر المؤثرين، نماذج الإسناد، إدارة التقارير والروابط، التصميم والجداول، أداء النظام وسرعة ظهور البيانات وسلاسة التفاعل، موافقات التسجيل والخصومات، التحكم بقنوات التحقق المدفوعة، إغلاق مشكلة Meta، ومعاينات المحتويات لجميع المنصات، وتصميم البريد الإلكتروني والرسائل الآلية والإشعارات والتنبيهات الدورية.  
**الأولوية:** P0 — متطلبات مالك المشروع؛ لا يجوز إسقاط أي بند.  
**الهدف:** إدارة الحملات الإعلانية والمتاجر والمؤثرين والتحليل والإسناد والتقارير التفاعلية من مكان واحد.

> **قاعدة ملزمة:** هذا الملف إضافة تراكمية لكل متطلبات CampaignsHub السابقة وليس بديلًا عنها. أحدث تصحيح صريح يلغي فقط الجزء المتعارض. يجب مطابقة جميع البنود بمصفوفة المتطلبات الموجودة فعليًا وبسجل ملاحظات المالك، مع عدم إعلان VERIFIED إلا بأدلة تنفيذ وتشغيل مناسبة. لا يجوز تحويل المتطلبات إلى وثائق فقط أو اعتبار نجاح CI إثباتًا على التشغيل الحي.

## 1. تسجيل الدخول — تصحيح صريح نهائي

- نقطة الدخول الوحيدة لجميع المستخدمين: `https://campaignshub.io/login`.
- لا يختار المستخدم بوابة؛ يحدد Backend الوجهة تلقائيًا حسب الحساب والعضوية والدور والصلاحيات وحالة الحساب والاشتراك.
- إزالة العبارة **«عميل لدى إحدى الوكالات؟ ادخل من بوابة العملاء»** والرابط والزر المشابهين من صفحة الدخول بالعربية والإنجليزية، وعدم عرض بديل يوحي بتجزئة الدخول.
- توجيه المدير إلى `/admin`، والمعلن/المتجر إلى `/app`، والوكالة إلى `/agency`، والعميل إلى `/portal`، مع `/switch` فقط عند وجود أكثر من مساحة مخولة يتطلب الاختيار بينها.
- الروابط القديمة مثل `/portal/login` يجب أن تنقل إلى مسار الدخول الموحد دون إتلاف روابط عودة صالحة أو توليد حلقات تحويل.
- الاحتفاظ بدخول عملاء الوكالة دون كلمة مرور باستخدام آلية رمز التحقق الملائمة ضمن تجربة الدخول الموحدة؛ المحافظة على تسجيل الدخول بالبريد وكلمة المرور وGoogle وخيارات OTP المدعومة، ومنع تعداد الحسابات.
- الحفاظ على عزل العملاء والوكالات وسلامة الجلسات بين التبويبات، والمنع الصارم لتسريب الصلاحيات.
- **القبول:** رحلة فعلية لكل نوع حساب، عربي/إنجليزي، جوال/كمبيوتر، متصفحات متعددة؛ لا redirect loops أو 401/419 غير مفسرة؛ الواجهة الصحيحة بعد الدخول والخروج.

## 2. Meta — إصلاح جذري مع دليل الحالة

**سؤال المالك: لماذا لم تُحل مشكلة Meta؟** لا تُعتبر الإجابة «Awaiting Credentials» دون تشخيص مثبت للمشكلة المحددة.

1. افحص حالة اتصال Meta الحالية لكل تطبيق/حساب/مشروع: OAuth، صلاحية الرموز، scopes، API access، account discovery، selected account binding، مزامنة الحملات والمجموعات والإعلانات والمحتويات والمؤشرات.
2. ميّز بدقة بين: عيب برمجي، Token منتهي، إذن ناقص، App Review/Business Verification، API limit، فشل مزامنة، نقص بيانات، خطأ واجهة.
3. أصلح فورًا ما يمكن إصلاحه داخل الكود، واختبر إعادة الاتصال والمزامنة والبيانات الحقيقية حيث تتوفر صلاحيات.
4. احتفظ بالتطبيقات والاتصالات الحية دون تبديل أو ترحيل أو كشف مفاتيح أو تغيير غير مصرح به.
5. لكل بند خارجي: اسم التطبيق/الحساب، scope، رسالة الخطأ/دليله، الخطوة المطلوبة من المالك أو Meta؛ التصنيف الصادق `BLOCKED_EXTERNAL_CREDENTIALS` أو `BLOCKED_OPERATIONAL_EVIDENCE`.
6. لا تقل Connected أو Synced أو Live من دون OAuth/API round trip ومزامنة وعرض بيانات حية مثبتة.

## 3. GA4 وتحليلات المتاجر — تطوير كامل بصري وتفاعلي

**ملاحظة المالك:** ربط Google Analytics 4 بالمتجر تقدم مهم، لكن الواجهة الحالية نصية وجدولية وطولية. المطلوب تحليلات **توازي عمق تقارير منصة سلة**، مع الرسوم والبطاقات والمؤشرات والعمل الحقيقي على مستوى النظام والتقرير.

### 3.1 مواضع الظهور

- داخل قسم **التحليلات** في النظام.
- تصنيف علوي واضح وقابل للإظهار/الإخفاء في **تقرير رابط (Live)** و**تقرير محفوظ (Snapshot)** باسم «تحليلات المتجر والزيارات» أو تصنيف مفهوم مكافئ.
- دعم التقارير القائمة وليس الجديدة فقط، بما فيها التقرير المحدد: `https://campaignshub.io/r/y5i0uUUyCowbZJZk49Sz5Y`، مع الحفاظ على الرابط ونطاق أذوناته.
- إظهار بطاقات ورسوم تحليلات وجداول مفيدة، لا نسخ الجداول المطولة كما هي.

### 3.2 مؤشرات Google Analytics 4

- المستخدمون، الجدد، النشطون؛ الجلسات، الجلسات المتفاعلة، معدل التفاعل، **معدل الارتداد**.
- متوسط مدة التفاعل، مشاهدات الصفحات، مشاهدات صفحات المنتجات، الصفحات المقصودة.
- القنوات والمصادر ووسائط الزيارات؛ التحويلات والأحداث الرئيسية.
- مشاهدة المنتج، الإضافة للسلة، بدء الدفع، الشراء، معدل التحويل، الإيرادات.
- **متوسط قيمة الطلب (AOV)** و**متوسط عدد المنتجات في السلة/الطلب**؛ الإيراد لكل مستخدم ولكل جلسة عندما تسمح البيانات.
- قيمة حالية، الفترة السابقة، التغير، اتجاه بياني، مصدر/تعريف كل KPI، حداثة البيانات وجودتها.

### 3.3 تحليلات المبيعات والمتجر بمستوى يوازي سلة

- إجمالي المبيعات وصافيها؛ إجمالي الطلبات، المؤكدة/المكتملة، الملغاة، المستردة؛ الخصومات، الشحن والضرائب إن وُجدت.
- متوسط قيمة الطلب، متوسط عدد المنتجات للطلب/السلة، معدل التحويل من زيارة إلى شراء، نمو المبيعات.
- أفضل المنتجات بالطلب والإيراد؛ التصنيفات؛ المنتجات ضعيفة الأداء؛ منتجات السلة المتروكة عند وجود البيانات.
- العملاء الجدد والعائدون، تكرار الشراء وقيمة العميل الزمنية عند وجود أساس موثوق؛ أثر الخصومات والإلغاءات والاستردادات.
- Funnel: زيارة ← مشاهدة منتج ← إضافة للسلة ← بدء دفع ← شراء؛ عدد ونسبة الانتقال والتسرب ومصدره.
- **المتجر مرجع الطلبات والمبيعات الفعلية**. اعرض GA4 والمنصات كلًا كمصدر مستقل للمقارنة، ولا تجمع الإيراد نفسه عدة مرات.

### 3.4 مصادر الزيارات وUTM

- Source / Medium، Session Source / Medium، First User Source / Medium عند الحاجة، Default Channel Group.
- `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`، Landing Pages، Referrals، Paid/Organic/Direct.
- الأداء حسب كل مصدر ووسيط وحملة وإعلان وصفحة هبوط ومؤثر ورابط مختصر: الجلسات، الزيارات، الإضافة للسلة، الطلبات المنسوبة بدليل، إيراداتها، معدل التحويل.
- مقارنة إحصائيات GA4 مع إحصائيات الإعلان والمتجر، وشرح الفروقات دون افتراض تطابق الأرقام.
- فلاتر متسلسلة ومسار drill-down من القناة إلى المصدر ثم الحملة/UTM ثم الصفحة/المؤثر؛ ربطها بالمشروع والحساب المصرح له فقط.

### 3.5 المخططات التفاعلية

- KPI Cards، Sparklines، Line/Area Charts، Bar/Stacked/Horizontal Bars، Donut/Pie، Funnel، الاتجاهات والمقارنة الزمنية، خرائط حرارية **عندما تُضيف قيمة تحليلية حقيقية**.
- توزيع الزيارات والمبيعات والقنوات والمنتجات والمصادر وUTM والحملات والمؤثرين، مع Tooltips وفلاتر تفاعلية وDrill-down.
- كل مخطط مرتبط بالبيانات المصرح بها والمرشحات الفعلية. لا رسوم شكلية أو demo مضلل أو نسب مشتقة متعارضة.

## 4. الجداول — إنهاء التمدد الطولي والتشتت

**عيب ملاحظ حيًا من المالك:** جداول مصادر الزيارات وUTM وغيرها تمتد طوليًا بصورة مشتتة.

1. Pagination فعلي، افتراضيًا 10 صفوف، واختيار 10/25/50؛ السابق/التالي وأرقام الصفحات وإجمالي السجلات.
2. فرز تصاعدي/تنازلي للأعمدة المناسبة، وبحث وفلاتر، واستبقاء الحالة عند التصفح/العودة حيث يلزم.
3. إظهار/إخفاء أعمدة، تقصير قيم UTM وأسماء الحملات الطويلة مع تفاصيل عند الطلب؛ رأس ثابت وتمرير داخل الجدول فقط عند الحاجة.
4. عرض ملخص بصري بالبطاقات والرسوم قبل تفاصيل الجدول، وفتح الصف لمزيد من البيانات دون إغراق واجهة التقرير.
5. أداء جيد مع آلاف الصفوف عبر Server-side pagination/sort/filter عند ملاءمة الحجم، ومنع اختلاط البيانات بين الصفحات أو تسرب نطاق غير مسموح.
6. توافق كامل مع 390px وDesktop وRTL/LTR وLight/Dark، دون تمرير أفقي للصفحة ككل.
7. لا تفقد تصديرات CSV/XLSX/PDF نطاق التقرير أو الفلاتر أو الأذونات بسبب ترقيم الصفحات في واجهة العرض.

## 5. نماذج الإسناد — مقارنة مبيعات المنصات بالمتجر

- أنشئ **قسمًا تفاعليًا مستقلًا قابلًا للإظهار أو الإخفاء بالكامل أو على مستوى أجزاء منه** داخل تحليلات النظام وتقرير الرابط والتقرير المحفوظ.
- المقارنة بين المبيعات المبلّغ عنها بواسطة Snapchat وTikTok وMeta وGoogle Ads وغيرها، ومشتريات GA4، وطلبات سلة/زد المؤكدة، والطلبات المنسوبة للمؤثرين، وغير المنسوبة، والمتعارضة.
- اعرض فروقات العدد والإيرادات والنسب، والطلبات الفريدة المؤكدة، والنماذج التي نُسبت بها النتائج، ومصدر الدليل، والفترة والمنطقة الزمنية ونافذة الإسناد.
- نماذج إسناد: `Basic` افتراضي، `Standard`، `Advanced` (غير مفعل افتراضيًا)، `Custom`؛ Last Eligible Click / Last Paid Click / Last Non-Direct Click / First Eligible Click / Linear / Position-Based / Time Decay / Custom Weighted، **فقط حين تتوفر Touchpoints وأدلة ربط كافية**.
- التحكم في Lookback Window، المصادر/القنوات المؤهلة، نافذة الإسناد، التكرار، الاستردادات، اختيار النموذج ومقارنة النماذج جنبًا إلى جنب.
- الرسم التحليلي: بطاقات فروقات، Trend، Donut/Stacked contribution، Breakdown، Funnel وجداول متعددة الصفحات، تنبيهات فروقات مادية وتفسير قصير مدعوم بالأدلة.
- **لا يُسمح بالادعاء أن نموذج الإسناد يلغي cross-platform overlap**؛ يقدم تفسيرًا وإسنادًا قائمًا على الأدلة مع حالة Unattributed/Unknown؛ لا يُخلق مسار مستخدم وهمي.
- الاستفادة من قدرات Thunder كمرجع وظيفي فقط، دون نسخ الكود/الخوارزميات الخاصة أو بيانات غير مصرح بها.

## 6. المؤثرون — قياس أثر الحملات بقدرات شبيهة بأثر

- ربط المؤثر بالعميل والمشروع والحملة، روابط تتبع خاصة، UTM، روابط قصيرة، QR، أكواد خصم، صفحات هبوط.
- قياس نقرات وزيارات مثبتة، إضافة للسلة، شراء منسوب بدليل، المبيعات المؤكدة من المتجر، تكاليف المؤثر والحملة إن وجدت، CPL/CPA/ROAS/ROI **عند صلاحية المعادلة**.
- لوحات بطاقات، اتجاهات، Funnel لكل مؤثر، تصنيفات وترتيب صعودًا وهبوطًا، جداول Pagination، مقارنة منصات ومؤثرين وUGC.
- كشف التداخل بين المؤثرين والإعلانات عبر نموذج الإسناد ودليل أحداث Tracking/Store، وبيان النتائج المجهولة.
- دمجها بتحليلات النظام وLive/Snapshot والتصديرات، مع صلاحية إظهار/إخفاء كل قسم ومؤشر واسم مؤثر.
- النقر على WhatsApp أو رابط المؤثر ≠ محادثة مؤكدة أو طلب أو عملية شراء. البيانات تتطلب إثباتًا مستقلًا.
- استخدام نظام التتبع الموجود وعدم إنشاء محرك موازٍ؛ «أثر» مرجع قدرات فقط دون نسخ غير مصرح به.

## 7. التحكم الشامل في إنشاء التقارير وبعد إنشائها

**قاعدة ملزمة:** جميع الإعدادات متاحة **قبل إنشاء التقرير وبعده**، ولـLive وSnapshot والقديم والجديد، حسب صلاحية المستخدم وحدود الرابط.

### 7.1 التحكم الدقيق

- الأقسام والتبويبات والتصنيفات، كل بطاقة KPI، كل Chart، كل Table، كل عمود، كل مؤشر وكل صف/كيان قابل لإخفائه حسب المنتج.
- أسماء العملاء والمشاريع والحسابات والحملات والمجموعات والإعلانات والمحتويات والمؤثرين؛ الأسعار والإنفاق والميزانيات والإيرادات والطلبات وUTM والمصادر والمنتجات ومقارنات الإسناد.
- GA4 والمتجر والمؤثرون والإسناد والروابط والرسوم والجداول والملاحظات والتوصيات.
- **إخفاء اسم حملة أو عمود الاسم لا يفرض إخفاء المقارنة أو الرسم أو القسم بأكمله.** يجب دعم تسميات عامة بديلة عندما تكون مطلوبة وبما لا يكشف الهوية في Tooltip/CSV/PDF/API.
- الصلاحيات مطبقة في Backend والـAPI والكاش والروابط المشتركة والتصدير، لا CSS فقط. لا كشف للأرقام أو الأسماء المخفية عبر إجماليات غير مسموحة.

### 7.2 وضع تلقائي + تعديل يدوي

- وضع تلقائي ذكي يختار أقسام ومؤشرات ملائمة لهدف الحملة والبيانات المتوفرة والصلاحيات، ولا يعرض غير المتوافق/الفارغ على أنه متاح.
- بعده يمكن إزالة أو إضافة أو إعادة ترتيب أي قسم أو مؤشر مناسب، تخصيص عدد Top-N والصفوف ونوع الرسم، وتغيير عنوان التقرير والفترة والمقارنة واللغة والعملة والهوية، مع معاينة فورية مطابقة لتجربة العميل.
- لا تحويل خيارات الإعداد إلى واجهة نصية مزدحمة؛ استخدم Presets وتحريرًا تدريجيًا مختصرًا ومرئيًا.
- يجب أن تختلف Executive Summary عن Detailed Report بنيويًا وعمقًا وليس بطول النص فقط.

## 8. إدارة التقارير والروابط القديمة والجديدة

لكل تقرير: **إنشاء، فتح، نسخ الرابط الحالي، مشاركة، تعديل، حفظ، إعادة تسمية، Duplicate، معاينة، تحويل النوع وفق الضوابط، إيقاف مؤقت، استئناف على نفس الرابط، إلغاء دائم، حذف مأذون، إدارة انتهاء الرابط والصلاحيات، سجل تعديل وزيارات.**

1. **نسخ الرابط القديم:** زر «نسخ الرابط» لأي تقرير قائم دون إجبار المستخدم على إنشاء رابط جديد؛ النسخ لا يبدّل نوع التقرير.
2. **تعديل نفس الرابط:** تعديل إعدادات التقرير والأقسام والمرشحات وإظهار/إخفاء الحقول وهوية التقرير دون تغيير URL المرسل سابقًا ما دام الوصول مُخوّلًا.
3. **Duplicate:** إنشاء نسخة مستقلة من إعدادات التقرير (المؤشرات والأقسام والهوية والنطاق **المصرح به**) مع تقرير ورابط جديدين؛ الأصلي ورابطه وسجله لا يتغيران.
4. **Live ↔ Snapshot:** تحويل مدروس وقابل للإدارة؛ Live يعرض بيانات متجددة، وSnapshot نسخة تاريخية ثابتة لا تُكتب فوقها بصمت. عند طلب التحويل مع بقاء الرابط يجب حماية النسخة التاريخية والتاريخ والأذونات والإعلان الواضح للمستخدم عن السلوك الجديد.
5. **إيقاف/استئناف:** الرابط نفسه، ويُمنع الوصول أثناء الوقف عبر الصفحة وAPI وPDF/CSV/XLSX ومصادر الكاش؛ الاستئناف لا يخلق رابطًا بديلًا، والإلغاء النهائي لا يُلغى ضمنيًا.
6. **الأذونات والتعديلات:** لا يُسمح بالتوسع الصامت في نطاق العميل/المشروع/الحساب أو إظهار بيانات كانت محجوبة؛ Audit trail لكل تعديل فعلي.
7. **التقرير المحدد:** `https://campaignshub.io/r/y5i0uUUyCowbZJZk49Sz5Y` يجب التحقق من معالجة وتحسين إعداداته وإتاحته دون تغيير رابطه أو البيانات التاريخية أو أذوناته بلا تصريح.
8. تصديرات PDF/CSV/XLSX يجب أن تُنتج ملفات قابلة للفتح وتطابق رؤية العميل وفلاتره ومصادر البيانات والهوية.

## 9. التصميم والتجربة

- صمّم منظومة موحدة احترافية: بطاقات KPI وسلاسل زمنية ورسوم خطية ومساحية وعمودية ودائرية ومسارات Funnel ومقارنات مرئية وجداول احترافية.
- استعمل التنقل التحليلي التدريجي: **بيانات → إشارة بصرية → مقارنة → تفسير مختصر → إجراء**.
- النصوص أقل قدر ممكن دون إخفاء الحقائق أو تحذيرات جودة البيانات؛ تجنب مئات البطاقات المتكررة والجداول الطويلة.
- مرشحات متسقة مع الفترة والعميل والمشروع والحساب والمنصة والهدف والمنتج والمصدر وUTM؛ تتغير البيانات الفعلية من Backend ولا يوجد fallback إلى كل البيانات.

## 10. الهدف الشامل والأسئلة التي يجب أن يجيب عنها النظام

## 12. P0 — أداء النظام وسرعة إظهار البيانات وسلاسة الحركة (إضافة صريحة من المالك 2026-11-03)

### 12.1 ملاحظة المالك كما وردت

> «النظام بطى جزء نظرا لحجم البيانات والادراج والمزامنة ، احتاج حل! بحيث عن فتح الصفحة مباشرة تظهر البيانات ، لاحظت تعلق الصفحة الى الانتظار ومن ثم تتحدث ، ايضا لاحظت الحركة بالنظام سريعة للماوس ليش ما يكون حركة زي الانظمة العالمية يبدو فيها بطئ قليل بالماوس او يعطي ايحاء للاحترافية العالية وليست واجهة ux فقط!»

**التفسير التنفيذي الملزم:** المطلوب إصلاح البطء الفعلي أولاً وإعطاء إحساس احترافي متزن بالتفاعل؛ ليس إبطاء حركة مؤشر الفأرة أو تعطيل الاستجابة عمدًا، وليس إظهار بيانات وهمية أو قديمة على أنها محدثة. هذا بند P0 مستقل يُسجل في مصفوفة التتبع وسجل العيوب الملحوظة، ولا يُغلق باعتبار أن تصميم الشاشة وحده تحسن.

### 12.2 العرض الفوري للبيانات عند فتح الصفحة

1. يجب أن تُظهر صفحات Dashboard/Analytics/GA4/Store/Campaigns/Reports/Integrations **آخر بيانات محفوظة ومصرحًا بها فور توفرها من التخزين المؤقت الآمن**، دون انتظار اكتمال المزامنة الخارجية؛ تُعرض حالة `آخر تحديث/آخر مزامنة` الحقيقية ووصف حداثة البيانات.
2. استخدم **stale-while-revalidate** أو نمطًا مكافئًا مُحكمًا: إظهار آخر نتيجة مؤكدة → تحديث في الخلفية → تحديث العناصر المتغيرة دون تفريغ الصفحة أو وميضها أو إعادة بنائها كاملًا.
3. في أول زيارة بلا بيانات مخزنة، أظهر هيكل تحميل ثابتًا للأجزاء المطلوبة فقط، مع مؤشرات تقدم/خطأ واضحة، ثم اعرض البيانات تدريجيًا بمجرد اكتمال كل جزء. لا تدّعِ وجود تحميل فوري من شبكة باردة عندما لا توجد بيانات محلية؛ ولا تُظهر Loading أبديًا.
4. لا تفرغ البطاقات والجداول والرسوم عند تغيير فلتر أو تبويب إذا أمكن الاحتفاظ بنتيجة صحيحة ضمن **نفس نطاق الصلاحيات والفلتر**؛ وتُعرض حالة التحديث بوضوح. يمنع إظهار بيانات فلتر/مشروع/حساب آخر أثناء الانتظار.
5. منع تسلسل تحميل متكرر بعد فتح الصفحة، وطلبات API المتطابقة، وتبدل الارتفاعات المربك، و`refetch`/`invalidate` المفرط، والانتظار العام قبل إظهار المحتوى المستقل.
6. الحفاظ على حيوية وفعالية البحث، التمرير، الفرز، الفلاتر، التبويبات والعودة أثناء تحديث البيانات.

### 12.3 فصل عبء الإدراج والمزامنة عن قراءة الصفحات

1. قياس من Production أو بيئة مماثلة لحجم بيانات فعلي: زمن API (`p50/p95`)، وقت الاستعلامات، عدد الاستعلامات، حجم الحمولة، وقت الرسم، زمن الاستجابة للتفاعل، الـCPU والذاكرة واختناق Queue/Horizon.
2. تحديد السبب الجذري لكل صفحة بطيئة: N+1، استعلامات تجميع متكررة، جداول ضخمة بلا فهارس مناسبة، pagination غير حقيقي، نقل payload مفرط، rerenders، تحديثات متسلسلة، منافسة العمال على موارد قاعدة البيانات أو سوء جدولة المزامنة.
3. الاستفادة من الفهارس وخطط `EXPLAIN ANALYZE`، تجميعات مسبقة/ملخصات مادية عند ملاءمتها، caching بمفاتيح تشمل tenant + project + authorized account scope + filters + time window + currency + permissions، وإبطال محدد وآمن؛ لا تستخدم cache عامًا يخلط العملاء أو يجعل تقريرًا محجوبًا قابلًا للوصول.
4. تطبيق pagination على مستوى API للجداول الطويلة، وتقسيم التحميل عند الحاجة، وvirtualization للقوائم الكبيرة، وتقسيم حزم الواجهة وتحميل الوحدات عند الطلب؛ تجنب تحميل كل الحركات والحملات والجلسات في أول زيارة.
5. عزل أعمال ingestion/sync الثقيلة في Queues مناسبة وتحديد التزامن والـbackoff والتوزيع الزمني وفق قدرة مزود البيانات والخادم، مع عدم تعطيل طلبات القراءة التفاعلية؛ عدم إعادة تنفيذ عزل الـQueues أو تحسينات ثبت أنها VERIFIED إلا عند عيب حقيقي.
6. أي تحسين لا يجوز أن يغيّر صحة الأرقام أو إسنادها أو مصدرها أو عزلها أو توقيت التحديث المعلن.

### 12.4 الإحساس الاحترافي بالحركة والتفاعل (Micro-interactions)

1. اعتماد حركات دقيقة **هادئة ومتسقة** لحالات Hover / Focus / Press / Open / Close / Filter / Tab / Drawer / Tooltip، لا انتقالات حادة أو قفزات مباغتة؛ لا تجعل المؤشر نفسه بطيئًا أو غير طبيعي.
2. اختيار مدد انتقال خفيفة ومدروسة (مرجع مبدئي: 120–220ms لعناصر التحكم، 180–300ms للألواح) وتعديلها بعد الاختبار، مع easing احترافي وحركات opacity/transform غير مكلفة؛ لا تزيد مدة التنفيذ الفعلية للزر أو التنقل انتظارًا للمؤثر البصري.
3. تمييز تفاعل الفأرة عن اللمس ولوحة المفاتيح، والحفاظ على وضوح التركيز وإمكانية الوصول، واحترام `prefers-reduced-motion`، وعدم تشغيل Hover في اللمس.
4. يظل التمرير طبيعيًا وسريع الاستجابة؛ لا تضف smoothing قسريًا يضعف التحكم، ولا motion-heavy libraries فقط لمظهر زخرفي، ولا تُبطئ تحميل الصفحات من أجل ظهور Animations.
5. المحافظة على ثبات تخطيط الواجهة (CLS) وإزالة الوميض/التبديل الحاد عند تحديث الرسوم والبطاقات والجداول.

### 12.5 معايير قبول قابلة للقياس وليست وعودًا غير واقعية

- أنشئ baseline موثقًا على **نفس الصفحة ونفس نطاق البيانات والحساب/المشروع ونفس الجهاز/الشبكة**، ثم قارن قبل/بعد: TTFB/API p50+p95، LCP، INP، CLS، زمن عرض أول KPI، وقت اكتمال أهم الرسم/الجدول، حجم payload، long tasks، ومعدل طلبات API المكررة.
- كأهداف أداء أولية **وليست ادعاءً بأن كل شبكة ستحققها**: LCP عند 2.5 ثانية أو أقل على بيئة الاختبار المستهدفة، INP عند 200ms أو أقل، CLS عند 0.1 أو أقل، مع تحديد وتوثيق أهداف API p95 حسب مسار القراءة الفعلي بعد القياس.
- عند إعادة فتح صفحة زارتها الجلسة بالفعل: آخر قراءة صحيحة في نطاق الصلاحيات تظهر دون انتظار الـsync، ويظل ختم آخر تحديث مرئيًا.
- عند أول فتح بارد: لا شاشة فارغة معلقة كما في صورة المالك؛ تظهر أجزاء مستقلة/هيكل تحميل سريع مع انتقال تدريجي إلى البيانات أو خطأ/حالة صريحة.
- تحت مزامنة خلفية ثقيلة: تستطيع تصفح GA4 والتقارير والمتجر وتبديل الفلاتر دون تجمد ملحوظ، ويجري اختبار حمل مشابه للإنتاج دون تعريض البيانات أو الإنفاق للخطر.
- اختبار فعلي على AR/EN، RTL/LTR، Dark/Light، 1366×768، 1440×900، جوال ~390px، Chromium/Firefox/WebKit، ومن دون حجب المحتوى بسبب حركة أو Overlay.
- تقارن الأدلة **الأداء الوظيفي وسلاسة الحركة كلًّا على حدة**؛ نجاح الاختبارات البصرية وحده لا يغلق P0 الأداء.

### 12.6 أولوية التنفيذ ومنع التجاوز

- افتح/حدّث Requirement ID لهذا المتطلب وملاحظة Owner مقابلة، واحتفظ بالنص الأصلي أعلاه داخل سجل التتبع؛ لا تكتفِ بإضافة هذا القسم إلى Markdown.
- ابدأ بعرض صفحة Analytics → GA4/المتجر ذات المساحة الفارغة/التعليق في لقطة المالك، ثم عمّم الحل على بقية الشاشات دون تكرار بنية caching/queries/animations.
- أكمل السبب الجذري → اختبار يعيد إنتاج البطء أو تأخر العرض → تحسين فعلي → قياسات قبل/بعد → اختبارات صلاحيات/بيانات/واجهة → PR/CI → Deploy → قياس Production. إذا تعذر إثبات أداء Production بحساب مخوّل، الحالة `BLOCKED_OPERATIONAL_EVIDENCE` أو `IMPLEMENTED_NOT_VERIFIED` كما يناسب، وليست `VERIFIED`.
- **هذا القسم إضافة ملزمة لجميع المتطلبات السابقة ولا يلغي أي شرط في الأقسام 1–11.**

## 13. P0 — الموافقة على طلبات التسجيل والتفعيل الكامل أو الجزئي (Owner 2026-11-03)

### 13.1 سير العمل المطلوب
1. تسجيل طلب حساب جديد وحالته دون منحه الوصول المدفوع تلقائيًا. عرض الطلبات في `/admin` ببحث وفلاتر وحالات وتاريخ الطلب وهوية مقدم الطلب والباقات والخدمات المطلوبة؛ منع تسجيل مدير منصة من التسجيل العام.
2. قرار المدير من نفس شاشة الطلب، بصلاحية صريحة وسجل تدقيق: **موافقة كاملة** على الحساب/الباقة/الميزات المصرح بها، أو **موافقة جزئية** تحدد بدقة الميزات والخدمات والصلاحيات والنطاق والمدة، مع **خصم محدد** (قيمة أو نسبة) أو إعفاء كامل أو فترة تجريبية وفق سياسة الاشتراكات المعتمدة؛ كذلك الرفض وطلب استكمال البيانات والتعليق وإلغاء القرار وفق الصلاحية.
3. لا يكفي ظهور زر «موافقة»: ينشئ القرار سجلًا حقيقيًا مرتبطًا بالطلب والحساب والباقة واشتراكه ومدفوعاته واستحقاقاته (Entitlements)، ويُعكس في Backend وحماية الواجهات والـAPI وسير الدفع والتفعيل، مع عدم توسيع الصلاحيات بسبب قيم قادمة من Frontend.
4. عند **الموافقة الكاملة**: الدخول إلى الواجهة المناسبة تلقائيًا **بعد تحقق شروط التفعيل**؛ وعند **الموافقة الجزئية**: لا تتاح إلا الموارد والخدمات الموافق عليها فعليًا، ويُعرض للمستخدم بوضوح ما تم تفعيله وما ينتظر الموافقة/الدفع.
5. الخصم يُطبّق حسابيًا على دورة الفاتورة وخط الدفع الصحيح، مع المبلغ الأساسي والخصم والصافي والعملة والمدة وتاريخ الانتهاء، والتحقق من أن الخصم لا يُطبق مرتين أو يتجاوز الحدود المسموح بها. لا يُعتبر طلب الموافقة حدث دفع موثوقًا؛ **لا تفعيل خدمة مدفوعة قبل Webhook/حدث دفع متحقق** إلا في حالة منح/إعفاء إداري مصرح به ومؤرشف.
6. إضافة/تعديل/إلغاء قرار الموافقة دون إفساد عضويات ومساحات قائمة، مع سياسة واضحة للمستخدمين الذين يملكون طلبات متزامنة أو طلبات قديمة أو اشتراكًا حاليًا؛ عمليات القرار Idempotent وتتعامل مع السباقات والتكرار والفشل الجزئي.
7. إشعارات نجاح/رفض/مطلوب إجراء مع قوالب بريد/SMS فقط عند تفعيل القناة، وسجل إرسال حقيقي؛ فشل قناة الإشعار لا يعني ادعاء وصول الرسالة ولا ينبغي أن يكرر الموافقة أو الدفع.

### 13.2 القبول الإنتاجي

## 16. P0 — إظهار المعاينة الفعلية لجميع المحتويات في جميع المنصات (Owner 2026-11-03)

### 16.1 نطاق العمل
- Meta وTikTok وSnapchat وGoogle Ads وLinkedIn وX وأي مزود متاح فعليًا، لكل حساب ومشروع مصرح به.
- أنواع المحتويات: صورة، فيديو، فيديو بلا غلاف، Story/Reel/9:16، Carousel، Collection، Dynamic Collection، Catalog/DPA، Multi-asset، النصوص والعناوين وصور مصغرة ومعاينة الإعلان الأصلية عندما تسمح واجهة المزود.
- كل موضع عرض حقيقي: **مكتبة المحتويات، البطاقة، نافذة التفاصيل، تفاصيل الحملة/المجموعة/الإعلان، تحليلات المحتوى، تقارير رابط Live، التقارير المحفوظة، PDF والتصدير الذي يدعم الوسائط**؛ نفس حقيقة الوسائط من resolver واحد، مع الحفاظ على ربط النتيجة والإنفاق والأداء بالمحتوى الصحيح.

### 16.2 الإصلاح الجذري لا النص البديل
1. اعمل **جرد Production لكل provider × format × surface**: العدد الكلي، معاينة قابلة للاستخدام/تشغيل، Missing Upstream، غير مستوردة، مفقودة في قاعدة البيانات، رابط منتهي، خطأ صلاحيات، خطأ تصنيف أو renderer؛ أسماء أمثلة واقعية بلا تسريب معلومات.
2. تتبع السلسلة كاملة: provider payload/API → pagination/discovery → creative assets/cards/tiles → ingestion → normalization → storage/signing/expiry/refresh → canonical resolver → API presenter → React UI/Player → Reports/Export.
3. إذا كانت الوسائط متاحة لدى المزود لكن النظام لم يجلبها/خزنها/عرضها، **إصلاح حقيقي ملزم**؛ لا تقبل عبارة «لا تتوفر معاينة» كحل في هذه الحالة. لا تخمّن response schema ولا تُدخل صورًا/فيديوهات وهمية.
4. اعرض الصور بدقة ونسبة أبعادها، وشغّل الفيديو الحقيقي بتفاعل المستخدم، وأظهر بطاقات Carousel/Collection والتنقل بينها. لا broken-image ولا مستطيلات فارغة ولا HTML share URL مستخدم كصورة، ولا قص شعار أو CTA في فيديو عمودي.
5. أعِد جلب الأصول المنتهية إن كان مزودها يدعم ذلك، مع حماية الصلاحيات والتوقيعات وعدم كشف token أو media private path أو حفظ دائم غير مصرح به.
6. عند عدم دعم المزود فعليًا لاسترجاع نوع معين أو وجود رفض خارجي موثق، أظهر حالة دقيقة مع السبب والإجراء؛ **100% تعني تغطية 100% من الأصول المتاحة المصرح بها وقابلة للاسترجاع، وليس تزوير معاينة لأصل لا يكشفه المزود**. يبقى الاستثناء الخارجي مفتوحًا بحالة BLOCKED مناسبة، ولا يجوز احتسابه متحققًا.
7. ضع مؤشرات للمعاينة الناقصة حسب المنصة/النوع، تنبيهات عند انهيار نسبة التغطية، وآلية إعادة المزامنة واستعادة الأصول المشروعة دون عمل مضاعف أو تحميل زائد عند كل فتح صفحة.

### 16.3 قبول غير قابل للتحايل
- إعادة إنتاج كل فشل حي عند مالك المشروع، ثم اختبار fail-first وإصلاح وإعادة قراءة أصل **حقيقي** من Meta/TikTok وغيرهما؛ اختبر الصورة والفيديو والقصة والكاروسيل والكتالوج والمجموعة متى كانت موجودة.
- تشغيل الفيديو بالفعل (`playing` مع تقدم `currentTime`)، وفحص صور حقيقية decode/content-type، والتنقل في بطاقات المجموعة، والتطابق بين البطاقة والتفاصيل والتقرير ورابط التقرير والـPDF حيث applicable.

- حافظ على العمل السابق VERIFIED في media resolver والعزل، وافتح/حدّث البنود الحالية في Matrix وOWNER_OBSERVED_DEFECTS بدل إنشاء وحدة موازية؛ تشمل الفجوات Content media/cover playback/expiry/collections/Meta catalog/TikTok ingestion حسب أدلة Git الحالية.

### 17.4 الإشعارات والتنبيهات الدورية والأتمتة
1. توفير **إعدادات إشعارات موحدة** في مساحة العمل ولوحة المدير حسب الصلاحيات، تشمل: داخل النظام والبريد وSMS إن كان متاحًا، وتمكين/تعطيل النوع، المستلم، المشروع/العميل/الحساب/الحملة، الأهمية، القناة، التوقيت والمنطقة الزمنية، والفترة: **فوري، يومي، أسبوعي، شهري**.
2. دعم إشعارات: انخفاض/ارتفاع الأداء، حدود الميزانية والإنفاق، فشل أو تأخر المزامنة، انقطاع الربط، بيانات GA4/المتجر المتأخرة، التنبيهات الحرجة، المهام والموافقات، والتقارير الأسبوعية/الدورية؛ بالاعتماد على بيانات حقيقية وصلاحيات صحيحة.
3. **Digest موحد** للفترات اليومية/الأسبوعية/الشهرية يقدم مؤشرات موجزة وبطاقات مفهومة وروابط آمنة إلى التفاصيل، مع التمييز الصارم بين نطاق مشروع واحد وبين **جميع المشاريع المصرح بها**؛ لا توسع نطاق التقرير عند تغيير خيارات المستخدم.
4. الجدولة والمهام الخلفية يجب أن تكون idempotent، فلا تكرر الإرسال بسبب retries أو إعادة تحميل صفحة، مع queue/retry/backoff، deduplication، وسجل حالات: queued / attempted / accepted / delivered (عند ورود دليل موثوق) / failed / suppressed، ودلالة واضحة لكل مرحلة. لا تعرض `Sent` أو `Delivered` من مجرد جدولة.
5. تمكين مراجعة القوالب ومعاينتها وإرسال **رسالة اختبار مخولة**، وتحديد/تعطيل تكرار التنبيهات المزعجة، احترام تفضيلات المستخدم وخيارات الإلغاء للإشعارات غير الضرورية، وعدم تمكين تعطيل الرسائل الأمنية الجوهرية بشكل يعرّض الحساب للخطر.
6. عند فشل SMTP، اعرض السبب الحقيقي بحالة تشغيلية وإجراء تصحيح، مع منع تسرب تفاصيل المصادقة أو الرموز؛ لا تُخفِ الفشل خلف إشعار نجاح شكلي.

### 17.5 معايير قبول الإنتاج الملزمة
- مقارنة بصرية **قبل/بعد** لقوالب الرسائل الأساسية، بالعربية والإنجليزية وعلى الهاتف والكمبيوتر وفي Gmail وOutlook وApple Mail بحسب أدوات الاختبار/الحسابات المتاحة؛ التحقق من التوسيط الصحيح للحاوية واتجاه النصوص وعدم القص والتمدد والتفاوت المشوه.
- تحقق من Subject يحمل `CampaignsHub`، اسم المرسل، الهوية البصرية، توازن المسافات، زر CTA، الرابط، التذييل، النسخة النصية، وجميع الأحداث التي تُولد الرسائل.
- اختبارات Backend/Frontend لجدولة التكرار ومناطق الزمن وتفضيلات المستلم والعزل ومنع التكرار وفشل الإرسال وإيقاف القنوات المدفوعة؛ إثبات عدم تسرب أي بيانات بين العملاء والمشاريع.
- إثبات تشغيل حي لرسالة معاملات وإشعار مجدول **من الإعداد إلى الاستلام** عند توفر قناة بريد حقيقية مخوّلة، مع قراءة السجل والرسالة المعروضة، وليس فقط قبول API أو نجاح Job. غياب اعتمادات/إذن استلام = `BLOCKED_EXTERNAL_CREDENTIALS` أو `BLOCKED_OPERATIONAL_EVIDENCE` دون ادعاء VERIFIED.
- ربط هذه المهمة بمعرّفات Matrix الموجودة لرسائل البريد والتنبيهات وDIGEST وWeekly Delivery، وإنشاء صف جديد فقط للفجوة غير الممثلة، والاحتفاظ بأي عيب Owner مفتوح حتى قبوله على Production.

## 18. قفل التنفيذ الشامل لهذه الإضافات دون إسقاط ما سبق

1. **الأقسام 1–17 جميعها ما زالت ملزمة**، بما فيها GA4، سلة/زد، الإسناد، المؤثرون، التعديل والتحويل بين Live/Snapshot، التقارير القديمة وروابطها، Pagination، أداء النظام، تسجيل الدخول، Meta، المعاينات، التسجيل والخصومات، وقنوات التحقق، والبريد الإلكتروني وقوالبه والتنبيهات الدورية.
2. عند بدء Claude Code: اقرأ هذا الملف كاملًا ثم ملفات مرجعية المشروع، وGit/HEAD/open PRs/CI/Production، و`docs/REQUIREMENTS_TRACEABILITY_MATRIX.md` و`docs/OWNER_OBSERVED_DEFECTS.md` و`docs/RESUME_STATE.md`؛ لا تعتمد على تقارير قديمة وحدها.
3. اربط **كل بند فرعي** بمعرّف Matrix موجود أو أضف معرّفًا فريدًا عند عدم وجوده، وسجل نص المالك ومعيار القبول وسطح التنفيذ والحالة ودليل Production والفجوة المتبقية. لا تكرر صفوف المتطلبات أو تُسقط أي بند بسبب نجاح الدفعة الأخيرة.
4. الأولوية: منع تسرب البيانات/الصلاحيات أولًا؛ ثم الإصلاحات P0 القابلة للتنفيذ بالأثر الأعلى؛ لا تؤجل الجميع بسبب Meta أو SMTP أو SMS أو موافقات API. راعِ تبعية كل جزء والاتصال بالمنتج المتكامل.
5. لكل دفعة صغيرة: عيب مثبت → اختبار fail-first حقيقي → أقل إصلاح صحيح في Backend/Frontend → اختبارات مركّزة + صلاحيات + browsers حسب الحاجة → PR/CI → merge → Deploy → Production acceptance → تحديث السجل؛ ثم استمر في الدفعة التالية.
6. ممنوع إعلان `VERIFIED` بناءً على كتابة الملف أو نجاح CI أو اكتمال Demo. الحالات المعتمدة فقط: `NOT_STARTED`، `IN_PROGRESS`، `PARTIAL`، `IMPLEMENTED_NOT_VERIFIED`، `VERIFIED`، `BLOCKED_EXTERNAL_CREDENTIALS`، `BLOCKED_OPERATIONAL_EVIDENCE`.
7. لا تُجرِ صرفًا إعلانيًا أو تعديلاً ماليًا أو تغيّر اتصالات Meta الحية أو تمسّ طلبات/بيانات Production دون تفويض مناسب. الموافقة الممنوحة لتنفيذ هندسة اعتيادية **لا تعني** موافقة على تغيير حساس أو غير قابل للاسترجاع.
8. خلاصة كل دفعة: ما نفذ + PR/SHA + نشر + دليل Production + البنود المتبقية بمعرّفاتها + العائق الدقيق؛ **لا تعلن اكتمال المهمة عالميًا حتى تستوفي جميع بنود 1–17 قبولها، وما يتطلب طرفًا خارجيًا يبقى مفتوحًا ومُصنّفًا لا يختفي**.
